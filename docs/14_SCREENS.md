# 14. Экраны, элементы и логика работы интерфейса

| Статус | Обновлён | Заменяет | Агенту |
|---|---|---|---|
| Действует | 2026-09-13 | дополняет `07_UI.md` (экраны) | Что должно быть на экранах и как это работает. Палитра, шрифты и стиль здесь не описываются: они у команды дизайна. Данные на экранах только из API (`05_API.md`); числа и идентификаторы с макетов — только композиция |

Документ адресован тому, кто делает макеты и фронтенд. Шесть готовых макетов
(`Проекты(Расчёт).png`, `Ошибка.png`, `Сеть.png`, `Отказы.png`, `Сравнение.png`,
`Результат_расчета.png`) задают композицию; ниже перечислено, чего в них не хватает,
чтобы пройти четыре сценария жюри (`01_SPEC.md` §6) и набрать баллы по критериям
«Удобство использования», «Работа с входными данными», «Проектирование и сравнение»,
«Анализ устойчивости» (`01_SPEC.md` §10).

Обозначения: **[есть]** — уже на макете; **[добавить]** — нужно добавить; **[изменить]** —
есть, но логика другая. «Модал» — всплывающее окно поверх экрана; «панель» — боковая
выдвижная область; «страница» — отдельный маршрут навигации.

## 0. Сквозные элементы (на всех экранах)

### 0.1 Шапка

- **[изменить] Навигация:** `Проекты | Сеть | Отказы | Исследования | Сравнение`.
  На макетах есть раздел «Результат»; он остаётся, но как **страница, куда ведёт
  завершённый расчёт**, а не как постоянный пункт меню (см. §6). «Исследования» (sweep,
  heatmap) на макетах нет — это обязательный P0-функционал (ADR-013), нужен отдельный
  экран (§5).
- **[добавить] Контекст проекта:** справа от логотипа выпадающий список
  `Проект › Вариант`. Показывает текущий проект и активный вариант; клик открывает
  список вариантов проекта с датой, `config_hash` (первые 8 символов) и статусом
  последнего расчёта. Смена варианта перезагружает экраны «Сеть», «Отказы»,
  «Сравнение». Источник: `GET /api/projects/{id}`.
- **[добавить] Индикатор расчёта:** маленький круговой прогресс в шапке, пока идёт хотя
  бы один Run (`GET /api/runs/{id}/events`, SSE). Клик раскрывает список активных
  расчётов с кнопкой «Отменить» (`POST /api/runs/{id}/cancel`). Пользователь может
  переключаться между экранами, не теряя расчёт.
- **[добавить] Баннер деградации:** если `GET /api/health` вернул
  `degraded_mode: true`, под шапкой тонкая полоса «Часть хранилищ недоступна: расчёты
  выполняются, история и трассы могут не сохраняться». Не модал, не блокирует работу.
- **[есть] Тема и настройки:** иконки справа. Настройки — модал: тема, язык подписей
  времени (`ЧЧ:ММ` / секунды), показ идентификаторов на карте, версия API и ядра
  (`GET /api/version`), состояние сервисов (`GET /api/health`).

### 0.2 Уведомления

- Тосты в правом нижнем углу, исчезают через 5 с, с кнопкой действия: «Расчёт
  завершён · Открыть результат», «Вариант сохранён», «Экспорт скачан», «Ошибка: … ·
  Повторить». Ошибки не исчезают сами, пока не закрыты.
- Подтверждения только для необратимого: удаление проекта, удаление варианта, отмена
  расчёта. Всё остальное без подтверждений, но с возможностью отменить действием
  «Сбросить изменения».

### 0.3 Понятия, которые интерфейс обязан различать

- **Сохранённый вариант** (Variant): неизменяемый, у него есть `config_hash` и может быть
  завершённый Run.
- **Черновик** (draft): любое изменение параметров на экране «Сеть» или «Отказы» делает
  текущее состояние черновиком. Черновик живёт в браузере, пока его не сохранили
  (`POST /api/projects/{id}/variants`) или не сбросили.
- **Результат расчёта** привязан к варианту и политике маршрутизации. Если черновик
  отличается от рассчитанного варианта, все результаты на экране помечаются как
  **устаревшие** (stale) полупрозрачным слоем и надписью «Параметры изменены — результат
  относится к сохранённому варианту. Рассчитать заново?» с кнопкой.

### 0.4 Состояния данных (обязательно у каждого блока)

Загрузка — скелетон формы блока; пусто — короткое объяснение и действие («Расчётов ещё
нет · Запустить расчёт»); ошибка — текст из `error.message` API и кнопка «Повторить»;
недоступно — блок затемнён с подсказкой, почему («Нужен завершённый расчёт»).

## 1. Экран «Проекты» (страница)

Назначение: войти в работу за 30 секунд: загрузить свой JSON или взять пример, увидеть,
что файл понят, и открыть проект.

### 1.1 Что есть на макете `Проекты(Расчёт).png` [есть]

Зона загрузки drag-and-drop с кнопкой выбора файла; четыре карточки примеров; правая
карточка с именем файла, статусом «Файл корректен», параметрами сценария (число
спутников, плоскостей, клиентов, шлюзов, горизонт, шаг, ISL) и списком наземных
объектов; кнопка «Открыть проект».

### 1.2 Что добавить

- **[добавить] Список недавних проектов** под примерами: карточки или строки
  «название · дата · число вариантов · последний расчёт (статус, худшая доступность)».
  Клик открывает проект (переход на «Сеть»). Меню строки: «Переименовать», «Удалить»
  (модал подтверждения), «Экспорт активного варианта». Источник: `GET /api/projects`.
  Пусто: «Проектов пока нет — загрузите сценарий или выберите пример».
- **[добавить] Название проекта** в правой карточке: поле, предзаполненное `meta.title`
  из файла, редактируемое до нажатия «Открыть проект».
- **[изменить] Правая карточка до загрузки файла**: пустое состояние с подсказкой
  «Перетащите файл или выберите пример — здесь появится обзор сценария». Во время
  проверки — скелетон и подпись «Проверяем сценарий…» (`POST /api/scenarios/validate`).
- **[добавить] Обзор сценария подробнее:** свернутая секция «Показать плоскости и
  спутники» → таблица плоскостей (id, RAAN, фаза, число спутников по очередям) и таблица
  наземных пунктов (id, название, роль, широта, долгота). Отдельно: число отказов и
  недоступностей шлюза в файле, если они есть («3 интервала отказов, 1 недоступность
  шлюза»).
- **[добавить] Примеры сценариев — четыре, не больше и не меньше:** названия и
  подписи берутся из `meta.title` файлов в `scenarios/`, а не зашиваются. Клик по
  примеру ведёт себя как загрузка файла: та же проверка, та же правая карточка.
- **[добавить] Кнопка «Открыть проект» создаёт проект** (`POST /api/projects`) и
  переводит на экран «Сеть» с активным вариантом. Повторная загрузка того же файла
  создаёт новый проект (без дедупликации: пользователь может хотеть чистый старт).
- **[добавить] Вторичное действие «Добавить как вариант в текущий проект»** — если
  проект уже открыт: загруженный файл становится новым вариантом
  (`POST /api/projects/{id}/variants`), diff от активного считается автоматически. Это
  нужно для сценария жюри №4: «изменённый сценарий выгрузить и загрузить повторно».

### 1.3 Модал ошибок валидации (`Ошибка.png`) [есть, уточнить]

- Заголовок с именем файла и числом ошибок; список: номер, JSON path, сообщение
  (из `errors[]` ответа 400). **[добавить]** код ошибки мелким текстом
  (`INVALID_SCENARIO_FIELD`) и, если есть, текущее значение из `details.value`.
- Кнопки: «Скачать отчёт» (текстовый файл со списком ошибок), «Выбрать другой файл»,
  **[изменить]** «Исправить и повторить» — открывает панель с **встроенным редактором
  JSON** (подсветка строк с ошибками по path, кнопка «Проверить снова»). Если редактор
  делать не будем, кнопка должна называться «Повторить проверку» и заново читать файл с
  диска (пользователь правит его во внешнем редакторе).
- Все ошибки списком, не первая (требование `01_SPEC.md` §3.1, `05_API.md` §3).

## 2. Экран «Сеть» (страница, основной)

Назначение: настроить конфигурацию, увидеть сеть в любой момент суток, маршрут клиента
и причину его отсутствия. Здесь проходят сценарии жюри №1 «Полная группировка» и
№2 «Этап развёртывания».

### 2.1 Левая панель — конфигурация

- **[есть] Выбор варианта**, этап запуска (1/2/3), плоскости с RAAN и фазой, кнопка
  «Добавить отказ».
- **[изменить] Плоскости:** RAAN и фаза оба редактируемые (на макете редактируется
  только фаза). Поле с шагом 1°, стрелки, ввод с клавиатуры, диапазон [0; 360).
  Число плоскостей берётся из сценария (у жюри их может быть не три).
- **[добавить] Параметры среды** в свернутой секции «Условия расчёта»: дальность ISL,
  минимальный угол возвышения, высота орбиты, наклонение, горизонт, шаг. По умолчанию
  только чтение; переключатель «Разрешить изменение условий» открывает поля с
  предупреждением: «Варианты с разными условиями не сравниваются напрямую»
  (`01_SPEC.md` §7).
- **[добавить] Политика маршрутизации:** переключатель `BFS (минимум переходов)` /
  `Удержание маршрута` / `Дейкстра по длине` с подсказкой в одну строку для каждой
  (ADR-003). Влияет на Run, не на вариант.
- **[добавить] Отказы:** список уже заданных интервалов (спутник, начало — конец,
  кнопка удалить); «Добавить отказ» открывает **модал** (§2.5). Отдельная строка
  «Недоступность шлюза» с тем же модалом для шлюзов.
- **[добавить] Строка состояния черновика:** «Есть несохранённые изменения» с
  кнопками «Сбросить» (вернуть к сохранённому варианту) и «Сохранить как вариант»
  (модал: название, по умолчанию генерируется из diff, например «P2 RAAN 60 → 72»).
- **[добавить] Кнопка «Предпросмотр»:** обновляет карту на текущем отсчёте для
  черновика без расчёта суток (`POST /api/preview`). Предпросмотр запускается
  автоматически через 500 мс после изменения любого параметра; кнопка нужна для
  явного повтора и для случая, когда автообновление отключено в настройках.
- **[изменить] Кнопка «Запустить расчёт»** переносится из правой панели в левую, под
  параметры: она действует на конфигурацию, а не на клиента. Если черновик не сохранён,
  кнопка сначала сохраняет вариант (модал названия), затем ставит расчёт
  (`POST /api/runs`). Пока расчёт идёт — кнопка превращается в прогресс со стадией
  («Маршрутизация · 412 из 720») и кнопкой «Отменить».

### 2.2 Центр — карта

- **[есть]** Земля в полярной проекции, плоскости, спутники с подписями, клиенты,
  шлюз, маршрут выбранного клиента.
- **[добавить] Легенда** в углу карты: активный спутник, отказавший (перечёркнут или
  иной маркер, не только цвет), клиент, шлюз доступный / недоступный, контакт
  клиент–спутник, ISL, выбранный маршрут, резервный маршрут.
- **[добавить] Слои** (переключатели в углу карты): «Все контакты» (все рёбра
  отсчёта; по умолчанию выключено, иначе каша), «Маршруты всех клиентов» (по
  умолчанию только выбранный), «Резервный маршрут» (`GET /api/runs/{id}/backup-paths`),
  «Подписи спутников», «Плоскости».
- **[добавить] Наведение на спутник:** подсказка: id, плоскость, очередь, состояние на
  отсчёте (активен / не запущен на этом этапе / отказ до ЧЧ:ММ), число контактов.
  **Клик по спутнику** открывает контекстное меню: «Задать отказ» (модал §2.5 с
  предзаполненным id), «Показать критичность» (переход на «Отказы» с этим спутником).
- **[добавить] Наведение на клиента:** доступность за сутки, статус на отсчёте,
  маршрут. Клик выбирает клиента (правая панель и подсветка маршрута).
- **[добавить] Подпись текущего момента** на карте: «06:00 · отсчёт 180 из 720».
- **[добавить] Состояние stale:** после правки черновика карта показывает предпросмотр
  черновика (это честные данные на одном отсчёте), а маршруты и доступность за сутки
  гасятся до нового расчёта.
- Данные: `GET /api/runs/{id}/snapshot?t_s=` для рассчитанного варианта,
  `POST /api/preview` для черновика.

### 2.3 Правая панель — клиенты

- **[изменить] Карточки всех клиентов**, не одного: для каждого клиента (число берётся
  из сценария) — id, доступность за сутки в процентах, цель (`target_availability`),
  достигнута/нет, максимальный перерыв, статус на текущем отсчёте («Связь есть · 4
  перехода» / «Нет связи · Разрыв межспутниковой сети»). Клик по карточке выбирает
  клиента.
- **[есть] Раскрытый клиент:** список узлов маршрута; **[добавить]** длина маршрута в
  км, число переходов, сколько отсчётов подряд держится этот маршрут (для политики
  удержания), кнопка «Резервный маршрут» (показывает второй непересекающийся путь и
  число резервов), кнопка «Перейти к первому перерыву».
- **[добавить] Блок причины, когда пути нет:** причина из enum человеческим текстом
  (`03_GLOSSARY.md` §3.1), доказательства: спутники, видимые клиенту; спутники, видимые
  шлюзу; аппараты в отказе; «последний рабочий маршрут в ЧЧ:ММ», «следующий в ЧЧ:ММ».
  Кнопка «Показать компоненты» подсвечивает на карте две изолированные группы
  спутников. Источник: `clients[].primary_cause/causes` в snapshot и
  `GET /api/runs/{id}/outages`.
- **[добавить] Сводка конфигурации** внизу панели: худшая доступность, худший
  перерыв, число перестроений маршрутов, клиенты, достигшие цели.
  Источник: `GET /api/runs/{id}/metrics`.

### 2.4 Нижняя шкала — таймлайн

- **[есть]** Трек на каждого клиента, зелёные/красные сегменты, маркер времени.
- **[добавить] Управление воспроизведением:** кнопки «в начало», «назад на отсчёт»,
  «играть/пауза», «вперёд на отсчёт», «в конец»; скорость ×1/×4/×16; клавиши
  `Space`, `←`, `→`, `Home`, `End`. Клик по шкале переводит карту на отсчёт.
- **[добавить] Оттенки причин:** сегменты без связи окрашены по `primary_cause`
  (четыре причины), легенда рядом со шкалой (на макете «Отказы» это уже есть, на
  «Сети» — нет).
- **[добавить] Наведение на сегмент:** подсказка «C70 · 12:20–12:44 · 24 мин · Нет
  связи со шлюзом». Клик по красному сегменту переводит на его первый отсчёт и
  раскрывает блок причины в правой панели.
- **[добавить] Маркеры отказов** над шкалой: интервалы отказов спутников и
  недоступности шлюза, чтобы было видно, где разрывы совпадают с отказами.
- **[добавить] Пометка краевых перерывов:** сегмент, упирающийся в 00:00 или 24:00,
  помечается «обрезан границей расчёта» (ADR-004).
- Данные: `GET /api/runs/{id}/timeline`.

### 2.5 Модал «Отказ спутника»

Поля: спутник (поиск по id, предзаполнен при вызове с карты), начало и конец в
`ЧЧ:ММ` с шагом 120 с (ползунок по шкале суток + два поля), подсказка «конец
исключительно». Проверки на месте: конец больше начала, внутри суток, спутник запущен
на выбранном этапе (иначе предупреждение: «Аппарат не активен на этапе 1 — отказ не
повлияет на расчёт»). Кнопки «Добавить», «Добавить и ещё один», «Отмена». Для шлюза —
тот же модал с выбором шлюза.

### 2.6 Прогресс расчёта

Не отдельный экран: левая кнопка показывает стадию и прогресс, шкала внизу
заполняется по мере `completed_ticks`, карта остаётся интерактивной на предпросмотре.
По завершении — тост «Расчёт завершён · Открыть результат» и автоматическое
обновление панелей. Ошибка расчёта — блок в правой панели с `error.message`, стадией и
кнопкой «Повторить».

## 3. Экран «Отказы» / Outage Detective (страница)

Назначение: задать отказ, увидеть, что изменилось, и понять причину каждого нового
разрыва. Сценарий жюри №3 «Отказ аппарата». Здесь жюри ставит 10 баллов за анализ
устойчивости.

### 3.1 Левая панель

- **[есть]** Выбор отказа, интервал, «Применить отказ», карточка спутника.
- **[изменить] Список отказов вместо одного:** таблица всех интервалов черновика
  (спутник, начало — конец, включён/выключен, удалить). «Добавить отказ» — модал
  §2.5. Пользователь может выключить отказ галочкой, не удаляя.
- **[добавить] Выбор с карты:** подсказка «Кликните спутник на карте, чтобы задать
  отказ». Спутники текущего маршрута выбранного клиента подсвечены как кандидаты
  (сценарий жюри: «выбрать спутник текущего маршрута»).
- **[добавить] База сравнения:** выпадающий список «Сравнивать с: последний расчёт
  варианта / выбрать расчёт». Кнопка «Применить отказ» = сохранить вариант с отказом +
  запустить расчёт + по завершении показать «после».

### 3.2 Центр — карта до/после

- **[есть]** Переключатель «До / После», маркер отказавшего спутника, момент времени.
- **[добавить] Режим «Рядом»:** две карты бок о бок на одном отсчёте (для широких
  экранов), иначе переключатель.
- **[добавить] Подсветка компонент:** при отсутствии пути после отказа кнопка
  «Показать разрыв» окрашивает спутники двух компонент разными маркерами и обводит
  клиент и шлюз. Это главный wow-момент (`07_UI.md`).
- **[добавить] Синхронный отсчёт:** переключение отсчёта меняет обе карты и обе шкалы.

### 3.3 Правая панель — что изменилось

- **[есть]** Карточка клиента «Маршрут перестроен», до/после, причина, влияние в п.п.,
  «Критические аппараты», «Рекомендация».
- **[добавить] Список затронутых клиентов:** для каждого — статус: «маршрут
  сохранился», «маршрут перестроен (N переходов → M)», «новый перерыв ЧЧ:ММ–ЧЧ:ММ,
  причина», дельта доступности и максимального перерыва. Незатронутые клиенты внизу
  серым. Источник: `POST /api/comparisons` c двумя Run.
- **[добавить] Кнопка «Открыть первый затронутый момент»** — переводит обе карты на
  первый отсчёт, где результат «после» отличается от «до».
- **[изменить] Критические аппараты — с данными, не списком имён:** для каждого:
  сколько клиентов теряют связь при его отказе на весь горизонт, на сколько п.п. падает
  худшая доступность, на сколько минут растёт худший перерыв, доля отсчётов, где он в
  минимальном разрезе. Кнопка «Проверить отказ» подставляет его в модал отказа.
  Источник: `POST /api/analysis/criticality` (запускается по кнопке «Рассчитать
  критичность», идёт до 30 с с прогрессом, результат кэшируется на Run).
- **[изменить] Рекомендация — только из расчёта:** текст собирается из данных
  («Отказ S31 в 06:00–24:00 снижает доступность C70 на 1,39 п.п.; маршрут перестроен
  через S12; резервный путь есть на 94 % отсчётов»). Общие фразы вроде «проверить
  резервные линии» не показываются. Если данных для рекомендации нет — блок скрыт.
- **[добавить] Кнопки:** «Сохранить как вариант», «В сравнение» (добавляет пару
  до/после на экран «Сравнение»), «Сбросить отказы».

### 3.4 Нижняя шкала

Две шкалы на клиента: «до» и «после» одна под другой, различия подсвечены (новые
красные сегменты — обводкой). Легенда причин. Маркер отказа над шкалой на весь
интервал.

## 4. Экран «Результат» (страница, открывается после расчёта)

Назначение: подытожить расчёт, сохранить, экспортировать, перейти к сравнению.
Сценарий жюри №4 в части «выгрузить».

- **[есть]** Заголовок «Расчёт завершён», карточки клиентов с доступностью, целью,
  максимальным перерывом; изменённые параметры; мини-карта; шкала; название варианта;
  «Скачать результат JSON», «Скачать сценарий JSON», «Перейти к сравнению».
- **[добавить] Параметры расчёта:** политика маршрутизации, версия ядра,
  `config_hash`, длительность расчёта, дата. Нужно для воспроизводимости и ответа на
  вопрос эксперта «а это тот же расчёт?».
- **[добавить] Таблица перерывов:** клиент, начало, конец, длительность, причина,
  «обрезан границей», кнопка «Показать на карте» (переход на «Сеть» на этот отсчёт).
  Источник: `GET /api/runs/{id}/outages`. Сортировка по длительности по умолчанию.
- **[добавить] Полные метрики клиента** в карточке: видимость, среднее и максимальное
  число переходов, число перестроений, число резервных путей (минимум), перерывы по
  причинам. Видимость рядом с доступностью объясняет разницу «спутник виден, но пути
  нет» — это ключевая мысль защиты.
- **[изменить] Мини-карта:** кликабельна, ведёт на «Сеть» на текущем отсчёте.
- **[добавить] Действия:** «Скачать Evidence Pack» (zip: экспорт, метрики, перерывы,
  сравнение, рекомендация — `GET /api/runs/{id}/evidence-pack`), «Повторить расчёт с
  другой политикой» (выпадающий список политик → новый Run того же варианта),
  «Открыть в сети».
- **[изменить] Название варианта:** редактируется здесь, сохраняется в Variant.
  Статус «Вариант сохранён» показывать только когда это правда (Run без сохранённого
  варианта невозможен, поэтому статус скорее «Расчёт привязан к варианту N»).
- Экспорт: файл `cosmo-A-result-1.0` скачивается как есть из
  `GET /api/runs/{id}/export`; сценарий — `GET /api/variants/{id}/export`. Имя файла:
  `<проект>_<вариант>_<политика>.json`.

## 5. Экран «Исследования» / Design Space Explorer (страница) [добавить целиком]

Назначение: перебрать сотни конфигураций автоматически и найти те, где все клиенты
достигают цели. 15 баллов «Проектирование и сравнение конфигураций» и 10 баллов
«Обоснованность рекомендаций».

### 5.1 Левая панель — постановка эксперимента

- Базовый вариант (текущий активный).
- Ось X: параметр (RAAN плоскости N, фаза плоскости N, этап запуска), диапазон от — до,
  шаг. Ось Y: то же или «нет» (одномерный sweep).
- Политика маршрутизации.
- Бюджет: максимум точек (по умолчанию 100, лимит из API), максимум времени.
  Подсказка: «≈ 0,3 с на точку, 100 точек ≈ 30 с».
- Кнопка «Запустить эксперимент» (`POST /api/experiments`); во время работы — прогресс
  «37 из 100 точек», кнопка «Остановить» (точки, которые успели посчитаться,
  остаются).
- Список прошлых экспериментов проекта: дата, оси, число точек, лучшая точка.

### 5.2 Центр — тепловая карта

- Heatmap X × Y, цвет = худшая доступность по клиентам (`min_client_availability`);
  контур целевого уровня (например 90 %). Для одномерного sweep — линейный график.
- Наведение на ячейку: значения параметров, худшая доступность, худший перерыв,
  клиент, который держит минимум. Клик — выбор точки (правая панель).
- Переключатель метрики цвета: худшая доступность / худший перерыв / средняя
  доступность / число перестроений.
- Второй график «Доступность против максимального перерыва»: точки эксперимента,
  выделен фронт компромиссов; подпись «наблюдаемая зависимость на рассчитанных
  точках», не «оптимум» (`07_UI.md`).
- Данные: `GET /api/experiments/{id}/points`.

### 5.3 Правая панель — точка

- Параметры точки, метрики по клиентам, отличие от базового варианта (дельты).
- Кнопки: «Сохранить как вариант» (`POST .../materialize` → Variant с diff),
  «Открыть в сети» (предпросмотр этой конфигурации), «В сравнение».
- Таблица «Лучшие точки» (топ-5 по правилу ранжирования ADR-006) с теми же кнопками.

### 5.4 Состояния

Пусто: «Экспериментов ещё нет — задайте ось и бюджет». Превышен бюджет: ошибка
`EXPERIMENT_BUDGET_EXCEEDED` с подсказкой уменьшить шаг или диапазон. Отменён:
показываются посчитанные точки, подпись «Остановлен на 37 из 100».

## 6. Экран «Сравнение» (страница)

Назначение: положить рядом два и более варианта и обосновать выбор. Сценарий жюри №4
«Изменение проекта» и №2 (полная группировка против первой очереди).

- **[есть]** Две карточки вариантов с доступностью по клиентам, график доступности,
  изменённые параметры, шкалы, рекомендация, «Поменять местами», «Применить вариант».
- **[изменить] Выбор вариантов:** сверху строка «Сравниваем: [вариант A ▾] [вариант B ▾]
  [+ добавить]». В списке — только варианты с завершённым расчётом той же политики;
  остальные серые с подписью «нет расчёта» и кнопкой «Рассчитать». До трёх–четырёх
  вариантов; первый — база. Источник: `POST /api/comparisons {run_ids}`.
- **[добавить] Таблица метрик с дельтами:** строки — клиенты и «конфигурация»;
  столбцы — варианты; в ячейке значение и дельта к базе (п.п. для долей, минуты для
  перерывов, число для переходов и перестроений). Метрики: доступность, видимость,
  максимальный перерыв, среднее число переходов, перестроения, резервные пути,
  достигнута ли цель. Проигранные показатели не скрываются (`09_DEMO_ECONOMICS.md`).
- **[изменить] Изменённые параметры — из diff, не вручную:** таблица `path · было ·
  стало` из `diff_from_parent`/сравнения канонических сценариев; если условия расчёта
  различаются (ISL, угол, высота) — предупреждение «Варианты с разными условиями:
  сопоставление ориентировочно».
- **[добавить] Шкалы рядом с общей осью времени** и синхронным маркером; клик по
  сегменту открывает «Сеть» на этом отсчёте для этого варианта.
- **[изменить] Рекомендация — из ранжирования:** блок показывает порядок критериев
  (`ranking_order`: худшая доступность → худший перерыв → средняя → резервы →
  перестроения → переходы), победителя, дельты по каждому клиенту, «цель достигнута /
  не достигнута; ближайшая точка отстаёт на X п.п.», ограничения («сетка 120 с,
  горизонт 24 ч, ISL 3000 км»). Источник: `GET /api/runs/{id}/recommendation?base_run_id=`.
  Если победитель — база, так и написать: «Изменение не улучшает худшего клиента».
- **[добавить] Сравнение политик маршрутизации:** переключатель режима «Варианты /
  Политики»: один вариант, три Run с разными политиками, те же столбцы плюс
  суммарная длина маршрутов. Отвечает на критерий «Алгоритмы маршрутизации».
- **[добавить] Происхождение вариантов (lineage):** свернутый блок с деревом
  вариантов проекта (`GET /api/projects/{id}/lineage`): кто из кого создан, что
  изменено, дельта худшей доступности на ребре. Клик по узлу подставляет его в
  сравнение.
- **[изменить] «Применить вариант»** = сделать его активным в проекте и перейти на
  «Сеть». **[добавить]** «Скачать Evidence Pack» (zip с экспортом обоих, сравнением и
  рекомендацией), «Скачать сравнение CSV».

## 7. Экран «Проект» (страница внутри «Проекты») [добавить]

Открывается кликом по проекту из списка. Содержит: название, дата, активный вариант;
таблица вариантов (название, создан, родитель, `config_hash`, изменённые параметры

политикой и статусом; дерево происхождения. Источник: `GET /api/projects/{id}`,
`GET /api/projects/{id}/lineage`. Это то место, куда пользователь «возвращается к
варианту» (`01_SPEC.md` §1 п. 8).

## 8. Прохождение сценариев жюри (что должно нажиматься)

1. **Полная группировка:** Проекты → пример «Полная группировка» → «Открыть проект» →
   Сеть: «Запустить расчёт» → прогресс → тост → карточка C-клиента → клик по клиенту →
   маршрут подсвечен → клик по шкале на 03:00, 12:00, 21:00 → маршрут меняется →
   «Перейти к первому перерыву» → блок причины с доказательствами.
2. **Этап развёртывания:** Сеть: этап 3 → 1 → предпросмотр обновился (спутников
   меньше) → «Запустить расчёт» (модал названия «Этап 1») → Результат → «Перейти к
   сравнению» → Сравнение: база «Полная группировка», кандидат «Этап 1» → таблица дельт
   и шкалы рядом → рекомендация: «цель не достигнута, отстаёт на X п.п.».
3. **Отказ аппарата:** Сеть: клик по спутнику текущего маршрута → «Задать отказ» →
   модал → Отказы: «Применить отказ» → прогресс → «После»: маршрут перестроен или
   перерыв → «Открыть первый затронутый момент» → «Показать разрыв» (две компоненты)
   → «Рассчитать критичность» → список критических аппаратов.
4. **Изменение проекта:** Сеть: RAAN плоскости 2: 60 → 72 → предпросмотр → «Сохранить
   как вариант» → «Запустить расчёт» → Сравнение с предыдущим → «Скачать сценарий
   JSON» → Проекты: «Добавить как вариант в текущий проект» тем же файлом → diff пустой
   → «Рассчитать» → тот же результат (дедупликация по `config_hash`, ответ 200 с тем же
   Run — интерфейс показывает «Такой расчёт уже есть»).

## 9. Чего на экранах быть не должно

- Чисел, идентификаторов и названий, зашитых в код: клиентов может быть не три,
  плоскостей не три, шлюзов больше одного, идентификаторы другие.
- Расчётов в браузере: доступность, перерывы, причины, дельты приходят из API.
- Кнопок без действия и разделов «скоро»: чего нет в API — нет и на экране.
- Единственного спиннера на весь экран: каждый блок грузится и ошибается отдельно.
- Статуса, закодированного только цветом: всегда иконка или подпись.
- Рекомендаций общими словами: только вычисленные дельты и условия.

## 10. Порядок реализации фронтенда (после макетов)

1. Каркас, навигация, контекст проекта, состояния блоков, клиент API по OpenAPI.
2. Проекты + модал ошибок + экран проекта.
3. Сеть: панель конфигурации, предпросмотр, запуск с прогрессом, карточки клиентов.
4. Карта и таймлайн с воспроизведением и причинами.
5. Результат и экспорт.
6. Отказы: до/после, компоненты, критичность.
7. Сравнение с дельтами, политиками, рекомендацией, lineage.
8. Исследования: эксперимент, heatmap, материализация точки.
