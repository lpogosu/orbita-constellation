## 2. Ядро: что и как устроено (4 минуты)

Говорим по цепочке, одна фраза на шаг, показывая `docs/15_STATUS.md` §2а или схему:

1. **Вход.** JSON `cosmo-A-1.0` проверяется целиком, все ошибки списком с путём до поля.
   Сценарий канонизируется и получает `config_hash`: одна конфигурация = один хеш = один
   результат.
2. **Геометрия.** Положения всех аппаратов на всех 720 отсчётах считаются одной векторной
   операцией NumPy по формулам кейса. Сверено с официальным `geometry.py`: расхождение
   10⁻¹² км.
3. **Контакты.** Видимость по углу возвышения (не меньше порога), ISL по дальности (строго
   меньше) и без пересечения Земли. Хранится как contact plan: список возможных рёбер и
   битовая матрица «отсчёты × рёбра». Сутки полной группировки — 34 КБ, сжато 5 КБ.
4. **Граф и маршрут.** На каждом отсчёте граф: клиенты, спутники, доступные шлюзы. Клиенты
   не ретранслируют. Три политики маршрутизации: BFS, удержание маршрута (то самое
   «обновление маршрута» из критериев, измеряется числом перестроений), Дейкстра по длине.
   Достижимость перепроверяется Union-Find: расхождение = ошибка расчёта, а не
   правдоподобный ответ.
5. **Причина разрыва.** Нет видимых спутников → шлюз недоступен → шлюз не видит
   спутников → разрыв межспутниковой сети. С доказательствами: кто кого видит, кто в
   отказе, последний и следующий рабочий маршрут.
6. **Метрики.** Видимость, доступность, максимальный перерыв с краевыми, переходы,
   перестроения, резервные пути и минимальный разрез через max-flow.
7. **Сравнение и рекомендация.** Лексикографический порядок: худший клиент → худший
   перерыв → средняя → резервы → перестроения → переходы. До/после отказа: новые,
   исчезнувшие, изменившиеся перерывы, где маршрут сохранился, первый момент расхождения.
8. **Выгрузка.** `cosmo-A-result-1.0` с маршрутом на каждую пару «отсчёт — клиент»;
   повторная загрузка даёт байт в байт тот же файл.

Что показать вживую (30 секунд, из папки `core/`):

```bash
python -m orbita_core golden ../scenarios
python -m orbita_core crosscheck ../scenarios/01_full_constellation.json --ticks 0,120,43200,86280
python -m orbita_core validate ../core/tests/fixtures/multi_errors.json
```

Фразы про проверку: «48 значений по четырём сценариям совпали с эталоном; ревьюер
независимо пересчитал по официальному модулю и проверил 8640 маршрутов на существование
рёбер; скрытый сценарий с другой структурой (5 плоскостей, 35 аппаратов, 2 шлюза, южный
клиент) проходит без правки кода».

## 3. Стек и почему он такой (внутри блока про ядро)

| Слой | Выбор | Почему, одной фразой |
|---|---|---|
| Ядро | Python 3.12 + NumPy, чистая библиотека без HTTP и БД | формулы кейса читаются как в PDF, векторизация по отсчётам даёт 0,25 с на сутки, ядро тестируется отдельно |
| Графы | свои BFS, Union-Find, Дейкстра, max-flow | графы малые, зависимость от NetworkX не нужна; NetworkX только как оракул в тестах |
| Трасса | bitset «отсчёты × рёбра» | 720 снимков JSON на точку перебора — сотни мегабайт, bitset — килобайты |
| API | FastAPI + Pydantic v2, OpenAPI как контракт | типы для фронтенда генерируются, документ и код сверяются тестом |
| Очередь | arq на Redis | расчёт вне веб-процесса, прогресс по SSE, отмена, идемпотентность |
| Postgres | проекты, варианты, запуски, метрики, перерывы | транзакции и история; дедупликация запусков по `config_hash + версия ядра` |
| MinIO | трассы, выгрузки, evidence pack | объекты с TTL; при росте до сотен аппаратов трасса не помещается в строку БД |
| Memgraph | контакты интервалами, происхождение вариантов | графовые запросы «какие аппараты во всех путях клиента»; необязателен для расчёта |
| Degraded | локальные адаптеры | без Redis, Memgraph и MinIO одиночный расчёт проходит целиком |
| Фронтенд | React 18 + TypeScript strict + Vite, Canvas 2D для карты | типы из OpenAPI, полотно макета 1920×1080 с масштабом под окно |

Сетка не зашита: число отсчётов, плоскостей, аппаратов, клиентов и шлюзов берётся из
файла. Замер на скрытом сценарии: 720 отсчётов — 0,25 с; 2880 (48 ч, шаг 60 с) — 1,1 с;
8640 (48 ч, шаг 20 с) — 4,6 с, битовая матрица 3 МБ. Предел горизонта 172 800 с
унаследован от официального `geometry.validate`.

Ограничения, которые называем сами: без пропускной способности и задержек; перебор
конфигураций — равномерная сетка; рекомендация детерминированная, без генеративных
моделей; при сотнях аппаратов нужен spatial pruning для ISL-пар (в плане).

## 3а. Где живут графовые данные (вопрос технического эксперта)

Три уровня, и все три в коде, не только в документах:

1. **Расчёт — в памяти ядра.** 720 графов суток строятся как contact plan: список возможных
   рёбер и битовая матрица «отсчёты × рёбра» (34 КБ на полную группировку, 5 КБ сжато).
   Обязательный расчёт в графовую БД не ходит: база не должна быть точкой отказа.
2. **Трасса — bitset в MinIO** (`runs/{id}/trace.bin`), не 720 JSON-снимков. Координаты не
   хранятся: восстанавливаются из сценария и времени. После истечения срока хранения
   трасса пересчитывается по `config_hash` и версии ядра.
3. **Memgraph + MAGE — для графовых запросов и происхождения.** Сохранённые запуски:
   `(:Run)-[:HAS_NODE]->(:Node)` и `[:CONTACT {start_tick, end_tick, min/max_distance_km}]`
   интервалами, а не ребром на отсчёт; варианты: `[:DERIVED_FROM {diff, дельты метрик}]`.
   Запросы, которые реляционная модель делает плохо: «какие аппараты входят во все пути
   клиента в интервале», мосты и двусвязные компоненты (MAGE), путь происхождения варианта.
   Выбран вместо Neo4j: in-memory, старт за секунды, Bolt-совместимость, алгоритмы из
   коробки (ADR-009). Для расчёта необязателен: без него работает пустой адаптер.
4. **Postgres** — метрики, перерывы, варианты, запуски: транзакции и агрегаты.

Рост (`06_STORAGE.md` §2): при 500 аппаратах 125 тысяч ISL-пар на отсчёт и трасса около
11 МБ — отсюда MinIO вместо строки БД и spatial pruning в ядре; перебор масштабируется
числом воркеров.

Ограничения называем сами: лицензия Memgraph BSL запрещает database-as-a-service (для
внутреннего инструмента не мешает); MinIO архивирован в 2026 году, в production заменяется
на SeaweedFS через тот же S3-адаптер.

## 5а. Зачем каждый экран (что говорить, открыв макет)

Сквозная логика: инженер загружает группировку → настраивает и считает → смотрит сеть и
маршруты → ломает её отказами и видит, что происходит → перебирает конфигурации →
сравнивает и получает рекомендацию → выгружает. Каждый экран — один шаг этого пути.

**Проекты.** Вход в работу за полминуты: свой JSON или один из примеров. Сразу видно, что
файл понят: сводка параметров, наземные пункты, а если в файле ошибки — список с точным
путём до поля, а не «файл некорректен». Зачем: критерий «работа с входными данными»
(10 баллов) и первое впечатление жюри, которое загрузит свой файл. Что сказать: «файл жюри
с другими идентификаторами и структурой проходит без правки кода».

**Сеть.** Главный экран: здесь видно, что группировка — это не спутники над головой, а
сеть, которая меняется каждые две минуты. Слева меняем этап запуска, ориентацию и фазу
плоскостей, политику маршрутизации, задаём отказы. В центре карта с полярной проекцией:
плоскости, спутники, контакты, маршрут выбранного клиента до шлюза. Справа карточки
клиентов: доступность за сутки, статус на текущем отсчёте, и когда пути нет — причина с
доказательствами. Внизу таймлайн: зелёное — путь есть, красное — нет, оттенок — причина;
клик переводит карту на этот момент. Зачем: критерии «корректность расчётов» и
«алгоритмы маршрутизации» (по 15 баллов) показываются здесь вживую: маршрут пересчитан на
каждом отсчёте, а переключение политики на «удержание» показывает, что маршрут не
дёргается без нужды. Что сказать: «спутник над пунктом ещё не значит связь: видимость
98 %, доступность 97 %, и мы показываем, где именно и почему эта разница».

**Отказы.** Ответ на вопрос «что будет, если аппарат выйдет из строя». Выбираем спутник
прямо на карте, задаём интервал, считаем повторно, видим «до» и «после»: у кого маршрут
перестроился, у кого появился перерыв и с какой причиной, с какого момента расчёты
расходятся. Блок критических аппаратов: без каких спутников связи не будет вовсе. Зачем:
критерий «анализ устойчивости» (10 баллов): не просто «маршрут отсутствует», а две
изолированные компоненты сети на карте и список затронутых направлений. Что сказать:
«это сценарий жюри номер три, и это то, что инженер делает руками сегодня по несколько
часов на вариант».

**Исследования.** Вместо ручного перебора «а если повернуть плоскость на 12 градусов» —
сетка по RAAN и фазе с бюджетом точек, тепловая карта худшей доступности с контуром 90 %,
лучшие точки, любую можно сохранить как вариант. Зачем: критерий «проектирование и
сравнение конфигураций» (15 баллов) и «обоснованность рекомендаций» (10): рекомендация
опирается на сотню посчитанных точек, а не на два варианта, придуманных руками. Что
сказать: «одна точка — 0,25 секунды, поэтому сто точек — полминуты; мы честно называем
это наблюдаемой зависимостью на рассчитанных точках, не оптимумом». Бэкенд этого экрана
в работе.

**Сравнение.** Два и более варианта рядом: доступность по клиентам с целью, дельты в
процентных пунктах и минутах, изменённые параметры из diff автоматически, таймлайны на
одной оси, рекомендация с порядком критериев и ограничениями. Проигранные показатели не
скрываются. Зачем: сценарии жюри номер два (этап развёртывания) и четыре (изменение
проекта), критерий «проектирование и сравнение». Что сказать: «рекомендация
детерминированная: худший клиент, потом худший перерыв, потом остальное; если цель не
достигнута, так и написано».

**Результат.** Итог расчёта одним экраном: метрики по клиентам, таблица перерывов с
причинами, параметры расчёта (политика, версия ядра, хеш конфигурации — чтобы любой
результат можно было воспроизвести), выгрузка результата и сценария, evidence pack.
Зачем: критерий «работа с входными данными» в части выгрузки и повторной загрузки, плюс
воспроизводимость перед техническим экспертом. Что сказать: «выгрузку можно загрузить
обратно и получить байт в байт тот же результат».

**Проект.** Куда возвращается инженер: варианты с diff от родителя, запуски с политикой и
статусом, происхождение вариантов. Зачем: кейс требует «сохранить вариант и вернуться к
нему»; для эксперта это ещё и ответ, откуда берётся история исследования.

Порядок показа в Figma на сессии: Проекты → Сеть → Отказы → Сравнение → Результат →
Исследования → Проект. Первые пять — путь жюри, последние два — глубина продукта.

## 6. Экономика (1 минута)

Base-сценарий из `13_ECONOMICS.md`, раздел «Для слайда»: пилот 4 FTE за 4 месяца,
production ещё 8 месяцев на 6 FTE; инфраструктура 17 тыс. ₽/мес пилот и 82 тыс. ₽/мес
production по прайсу VK Cloud; лицензии 0 ₽; экономия 5 часов инженера на вариант;
payback 22,5 месяца, ROI первого года 257 %; порог окупаемости 112 вариантов в год.
Одна фраза: «зарплаты по медианам Хабр Карьеры, взносы по закону 2026 года, единственное
допущение, которое двигает окупаемость, — часы инженера на вариант; его и хотим уточнить».

## 8. Что не говорим

Не обещаем 90 % во всех условиях; не называем перебор «оптимизацией»; не углубляемся в
детали процесса разработки.
