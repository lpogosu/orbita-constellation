## Раздел 1. Проектирование и анализ группировки

### 1. Проектирование и сравнение конфигураций — до 15

**Что требуется.** Выбирать этап развёртывания, изменять параметры плоскостей, сравнивать
варианты. Результат сравнения должен помогать выбрать конфигурацию для заданных наземных
пунктов.

**Чем закрыто.**

| Требование | Реализация |
|---|---|
| выбор очереди запуска | переключатель `launch_stage` 1 / 2 / 3 на экране «Сеть» — `web/src/features/network/ConfigCard.tsx`; в расчёте активны аппараты с `launch_batch <= launch_stage` — `core/orbita_core/contacts.py` |
| ориентация плоскостей | поле `raan_deg` каждой плоскости, там же; правка идёт в черновик варианта — `web/src/features/network/draft.ts` |
| фазирование | поле `phase_deg` каждой плоскости, рядом с RAAN |
| периоды недоступности аппаратов | модал добавления отказа — `web/src/features/network/FailureModal.tsx`; недоступность шлюзов — `gateway_outages` в том же черновике |
| сохранение варианта и возврат к нему | `POST /api/projects/{id}/variants`, список вариантов проекта — экран «Проект», `web/src/features/project/VariantsCard.tsx` |
| сравнение вариантов | `POST /api/comparisons` — метрики рядом, `changed_parameters` с точным путём изменённого поля и `deltas` по каждой метрике; экран «Сравнение» |
| помощь в выборе | карточка рекомендации: лучший кандидат, дельты по клиентам, достигнута ли цель, ограничения — `GET /api/runs/{id}/recommendation`, `core/orbita_core/ranking.py` |
| автоматический подбор (дополнительная функциональность) | одномерный и двумерный перебор параметров с бюджетом, тепловая карта доступности худшего клиента, выбор точки как варианта — экран «Исследования», `core/orbita_core/sweep.py` |

Сравнение всегда идёт на одной сетке времени: запуски с другим `step_s`, `horizon_s`,
`isl_range_km` или `min_elevation_deg` из сравнения исключаются с явной ошибкой и путём к
расхождению (`core/orbita_core/compare.py`).

**Как проверить.**

1. На экране «Сеть» переключить очередь с 3 на 1, сохранить вариант, рассчитать.
2. Вернуть очередь 3, изменить `raan_deg` одной плоскости, сохранить второй вариант.
3. Экран «Сравнение»: выбрать два запуска. В таблице видны изменённое поле, метрики рядом
   и дельты; ниже — рекомендация.

Тот же цикл через API — раздел «Полный цикл через API» в `README.md`.

### 2. Анализ устойчивости — до 10

**Что требуется.** Полнота анализа отказов: какие направления связи затронуты, где
сохраняется маршрут, как меняются перерывы. Объяснение уязвимостей и способы повышения
устойчивости.

**Чем закрыто.**

- **Причина каждого перерыва.** `core/orbita_core/diagnosis.py` разбирает отсчёт без
  маршрута и называет причину из четырёх, заданных кейсом: `NO_CLIENT_COVERAGE` (нет
  видимого спутника), `NETWORK_PARTITION` (разрыв межспутниковой сети),
  `NO_GATEWAY_COVERAGE` (нет контакта со шлюзом), `GATEWAY_OUTAGE` (шлюз недоступен).
  Причины не срабатывают вхолостую: `NO_GATEWAY_COVERAGE` проверяется только при наличии
  доступного шлюза, `NETWORK_PARTITION` — только когда обе стороны видимы.
- **Сеть до и после отказа.** Экран «Отказы» считает два запуска на одном проекте и
  показывает их рядом: затронутые клиенты, первый момент расхождения маршрутов, новые и
  исчезнувшие перерывы — `web/src/features/outages/`,
  `api/orbita_api/services/comparisons.py`.
- **Где маршрут выживает.** Резервные пути считаются max-flow с расщеплением вершин:
  `GET /api/runs/{id}/backup-paths` возвращает число независимых путей и минимальный
  разрез — список аппаратов, отказ которых обрывает связь. Это прямой ответ на вопрос
  «где сохраняется маршрут».
- **Рейтинг критичности аппаратов.** `core/orbita_core/resilience.py`: перебор отказа
  каждого спутника, ущерб по доступности худшего клиента, точки сочленения графа
  контактов. Endpoint `POST /api/analysis/criticality`, карточка критичности на экране
  «Отказы».
- **Уязвимости и способы повышения устойчивости** — одноимённый раздел
  [`19_ANALYSIS.md`](19_ANALYSIS.md), с числами из наших же расчётов.

**Как проверить.** Экран «Отказы»: выбрать спутник текущего маршрута, задать период
недоступности, пересчитать. Появляются список затронутых клиентов, изменение перерывов,
новый маршрут или причина его отсутствия.

### 3. Обоснованность рекомендаций — до 10

**Что требуется.** Связь рекомендаций с расчётами; преимущества выбранного проекта,
условия достижения целевой доступности, ограничения применения.

**Чем закрыто.**

- [`19_ANALYSIS.md`](19_ANALYSIS.md) — инженерный разбор: базовая линия по четырём
  сценариям кейса, достижение цели 90 %, влияние очереди запуска и дальности ISL, разбор
  отказов, перебор конфигурации, сравнение политик маршрутизации и, отдельным разделом,
  рекомендации с условиями и ограничениями. Все числа получены запуском ядра; скрипты и
  сырые результаты — в `docs/analysis/`.
- Рекомендация внутри сервиса не декларативна, а вычислена: `core/orbita_core/ranking.py`
  ранжирует кандидатов по доступности худшего клиента, затем по максимальному перерыву, и
  возвращает `target_reached` вместе со списком `limitations` — условий, при которых
  результат получен (сетка, дальность ISL, порог возвышения).
- Кандидатами берутся только сравнимые запуски: тот же проект, та же политика
  маршрутизации, те же параметры среды. Несравнимое сравнение отвергается ошибкой.
- Evidence Pack (`GET /api/runs/{id}/evidence-pack`) — zip из выгрузки, метрик, перерывов и
  версии ядра: рекомендацию можно приложить к отчёту и воспроизвести.

**Как проверить.** Прочитать [`19_ANALYSIS.md`](19_ANALYSIS.md); числа сверить командой
`python -m orbita_core golden scenarios` и скриптами `docs/analysis/`.

## Раздел 2. Удобство использования

### 4. Удобство использования — до 10

**Что требуется.** Понятность настройки проекта, работа с временной шкалой, наглядность
покрытия и маршрутов, удобство сравнения; эксперт должен пройти основные сценарии.

**Чем закрыто.** Семь экранов, каждый под свою задачу:

| Экран | Адрес | Задача |
|---|---|---|
| Проекты | `/projects` | загрузка сценария перетаскиванием, четыре примера кейса, недавние проекты, разбор ошибок файла |
| Проект | `/projects/{id}` | варианты проекта, запуски, происхождение вариантов |
| Сеть | `/network/{id}` | конфигурация варианта, карта группировки на выбранном отсчёте, маршруты клиентов, шкала суток |
| Отказы | `/outages/{id}` | сеть до и после отказа, затронутые клиенты, причины разрывов, критичность аппаратов |
| Исследования | `/experiments/{id}` | перебор параметров с бюджетом, тепловая карта, выбор точки как варианта |
| Сравнение | `/comparison?project={id}` | метрики вариантов рядом, дельты по клиентам, рекомендация |
| Результат | `/result/{runId}` | метрики расчёта, окна перерывов, покрытие маршрутов, выгрузка |

- **Карта.** Два режима: плоская карта на Canvas 2D и трёхмерный глобус на three.js —
  спутники, наземные пункты, доступные линии связи, выбранный маршрут, компоненты
  связности. Глобус вращается мышью, положение аппаратов соответствует выбранному отсчёту.
- **Временная шкала.** Ползунок на 720 отсчётов суток; диаграмма доступности по каждому
  клиенту показывает интервалы связи и перерывы — `web/src/timeline/Timeline.tsx`.
- **Состояния интерфейса.** Загрузка скелетонами, пустое состояние с объяснением, ошибка с
  повтором, недоступное действие — `web/src/components/state/`.
- **Первый запуск.** Обучающий тур по разделам —
  `web/src/components/onboarding/OnboardingTour.tsx`.
- **Сброс изменений и новый запуск** — кнопка «Сбросить» на карточке конфигурации.

**Как проверить.** Базовые сценарии кейса на живом сервисе: полная группировка, маршрут в
нескольких моментах, переключение очереди, отказ аппарата, изменение ориентации плоскости,
сравнение. Подробный проход — в [`14_SCREENS.md`](14_SCREENS.md).

## Раздел 4. Расчётная модель и маршрутизация

### 6. Корректность расчётов — до 15

**Что требуется.** Соблюдение правил расчёта координат, видимости, состава активных
аппаратов и доступности связей. Показатели покрытия и перерывов должны соответствовать
состояниям сети на расчётной сетке.

**Чем закрыто.**

| Правило кейса | Реализация |
|---|---|
| круговые орбиты, сферическая Земля, `r = R + h`, `n = √(μ/r³)` | `core/orbita_core/geometry.py`; константы `R = 6371`, `μ = 398600.435507`, `T = 86164.09054` |
| инерциальные координаты и поворот в земную систему через `θ = earth_angle0 + 2πt/T` | там же, `positions_all` — сразу на всех 720 отсчётах, без цикла по времени |
| угол возвышения `arcsin(((s − g)·g)/(‖s − g‖·R))`, контакт при угле **не ниже** порога | `elevation_all`; сравнение `>=`, как в кейсе |
| ISL при `‖b − a‖ < isl_range_km` и расстоянии от центра Земли до отрезка больше `R` | `isl_visible_all`; дальность строго `<`, проверка отрезка через `q = clip(−a·d/(d·d), 0, 1)`, при совпадении координат — `‖a‖` |
| состав активных аппаратов: `launch_batch <= launch_stage` минус периоды недоступности | `core/orbita_core/contacts.py`; недоступный аппарат сохраняет положение и исключается из связей |
| сетка 0, 120, …, 86 280; правый конец не включается; интервалы `[start; end)` | `core/orbita_core/scenario.py`, `ticks` и `times_s` |
| доли = число отсчётов, делённое на общее число; максимальный перерыв = длиннейшая серия × `step_s` | `core/orbita_core/metrics.py` |
| число переходов = число рёбер маршрута, включая две наземные линии; при отсутствии пути отсутствует | там же |

**Чем это подтверждено.**

1. **Сверка с официальным расчётным модулем.** `python -m orbita_core crosscheck` считает
   позиции и рёбра нашим ядром и эталонным `case/geometry/geometry.py`, затем сравнивает.
   Максимальное расхождение позиций — **9,1·10⁻¹³ км**, расхождений в составе рёбер —
   **0** на отсчётах 0, 120, 43 200, 86 280. Это машинная точность: реализации совпадают.
2. **Golden-значения.** `python -m orbita_core golden scenarios` сверяет 48 величин
   (четыре сценария × три клиента × четыре показателя) с таблицей
   [`10_FIXTURES.md`](10_FIXTURES.md) §1: **48 проверок, 0 расхождений**.
3. **Тесты ядра.** 438 тестов, включая краевые случаи порогов (`min_elevation_deg` ровно
   на границе, дальность ISL ровно `isl_range_km`), инварианты метрик и согласованность
   маршрутов с составом рёбер.

**Как проверить.**

```bash
python -m orbita_core crosscheck scenarios/01_full_constellation.json --ticks 0,120,43200,86280
python -m orbita_core golden scenarios
```

### 7. Алгоритмы маршрутизации — до 15

**Что требуется.** Поиск и обновление допустимых маршрутов, обработка разрывов и отказов,
обоснованность подхода. Команда объясняет алгоритм и показывает его работу при изменении
сети.

**Чем закрыто.**

- **Три политики** (`core/orbita_core/routing.py`, enum `RoutingPolicy`):

  | Политика | Что делает | Когда применять |
  |---|---|---|
  | `bfs_shortest` | обход в ширину до первого достигнутого доступного шлюза — минимум переходов | база: меньше переходов, меньше точек отказа |
  | `persistent` | удерживает прежний маршрут, пока все его линии существуют и шлюз доступен; ищет заново только при разрыве | меньше переключений маршрута, важно для сеанса передачи |
  | `dijkstra_distance` | кратчайший по сумме длин линий | оценка задержки распространения |

- **Обновление при изменении сети.** Маршруты считаются на каждом из 720 отсчётов заново
  по contact plan этого отсчёта, поэтому движение аппаратов, смена очереди запуска и
  периоды недоступности учитываются без отдельного механизма. `persistent` дополнительно
  проверяет пригодность удержанного маршрута (`_still_valid`).
- **Разрывы объясняются, а не просто фиксируются** — четыре причины кейса, см. критерий 2.
- **Независимая проверка.** Результат поиска пути сверяется с Union-Find по тому же набору
  рёбер: если достижимость по компонентам связности и найденный путь расходятся, расчёт
  падает с `InternalInconsistencyError`, а не выдаёт молча неверный ответ. Это вторая,
  независимая реализация ответа на вопрос «есть ли путь».
- **Резервные пути.** Max-flow с расщеплением вершин даёт число вершинно-независимых
  маршрутов и минимальный разрез — `core/orbita_core/graph.py`.
- **Обоснование выбора** — [`02_DECISIONS.md`](02_DECISIONS.md) и раздел «Политики
  маршрутизации» в [`19_ANALYSIS.md`](19_ANALYSIS.md), где три политики сравнены числами
  на сценарии кейса.

**Как проверить.**

```bash
python -m orbita_core run scenarios/01_full_constellation.json --policy bfs_shortest      --out a.json
python -m orbita_core run scenarios/01_full_constellation.json --policy persistent        --out b.json
python -m orbita_core run scenarios/01_full_constellation.json --policy dijkstra_distance --out c.json
```

В интерфейсе: экран «Сеть», выбрать клиента и провести ползунком по суткам — маршрут
перестраивается на каждом отсчёте, при отсутствии пути показывается причина.

## Раздел 5. Работа с данными

### 8. Работа с входными данными — до 10

**Что требуется.** Загрузка дополнительных сценариев, применение изменений из интерфейса,
корректный повторный расчёт, сохранение параметров, выгрузка результата, понятные
сообщения об ошибках.

**Чем закрыто.**

- **Загрузка.** Экран «Проекты»: перетаскивание файла или выбор одного из четырёх примеров
  кейса. Формат `cosmo-A-1.0`; жюри может загрузить свой файл того же формата.
- **Валидация по всем правилам кейса** — `core/orbita_core/scenario.py`: конечность чисел,
  уникальность идентификаторов, разрешимость ссылок на плоскости и аппараты, целые
  положительные `horizon_s` и `step_s`, кратность горизонта шагу, интервалы недоступности
  внутри периода расчёта и положительной длительности, различие идентификаторов наземных
  пунктов и спутников.
- **Понятные сообщения.** Ошибки собираются **списком**, а не по одной, каждая — с кодом и
  путём в точечной нотации (`design.planes[1].raan_deg`, `failures[0].end_s`). В интерфейсе
  — модал разбора с подсветкой проблемного места и встроенным редактором JSON, чтобы
  поправить файл и повторить загрузку не выходя из экрана
  (`web/src/features/projects/ValidationErrorsModal.tsx`).
- **Применение изменений и повторный расчёт.** Правки конфигурации идут в черновик,
  сохраняются вариантом и считаются заново; повторный запуск той же конфигурации не
  пересчитывается, а переиспользует готовый результат по `config_hash` и `engine_version`.
- **Сохранение параметров.** `effective_scenario` в выгрузке содержит полный сценарий,
  которым считали, включая изменения пользователя.
- **Выгрузка.** `GET /api/runs/{id}/export` и кнопка «Скачать результат JSON» дают файл
  `cosmo-A-result-1.0`: `effective_scenario` и `routes` — по одной записи
  `{t_s, client_id, path}` на каждую пару «отсчёт — клиент» (2160 записей для трёх
  клиентов), пустой `path` при отсутствии маршрута. Дополнительно в файле метрики, перерывы
  и рекомендация.
- **Замкнутость.** Выгруженный `effective_scenario` снова проходит валидацию и даёт тот же
  `config_hash` — файл можно загрузить обратно в сервис.

**Как проверить.**

```bash
curl -s -X POST localhost:8000/api/scenarios/validate -H 'Content-Type: application/json' \
  --data-binary @scenarios/01_full_constellation.json | jq .
curl -s localhost:8000/api/runs/$RUN/export -o export.json
jq .effective_scenario export.json | curl -s -X POST localhost:8000/api/scenarios/validate \
  -H 'Content-Type: application/json' -d @- | jq .
```

Испорченный файл (например, ссылка на несуществующую плоскость) даёт 400 со списком всех
найденных ошибок.

## Раздел 6. Качество кода и документация

### 9. Качество кода — до 5

**Что требуется.** Структура проекта, читаемость, разделение расчётной логики и интерфейса,
возможность проверить ключевые функции.

**Чем закрыто.**

- **Расчёт отделён от всего остального.** `core/orbita_core` — чистый Python 3.12 и NumPy,
  без HTTP, без ORM, без знания о базе и очереди. `api/` и `worker/` вызывают его как
  библиотеку, фронтенд не считает ничего. Ядро работает из командной строки без стека —
  это и есть проверка разделения.
- **Строгая типизация.** `mypy --strict` для Python, `strict: true` и запрет `any` для
  TypeScript, `ruff` и `eslint` в CI.
- **Проверяемость ключевых функций.** 438 тестов ядра, 129 тестов API, тесты воркера;
  отдельно — сверка с эталонным расчётным модулем и golden-значения (критерий 6).
- **Одна команда проверок.** `make test` собирает тот же образ, что и сервисы, и гоняет в
  нём линтеры, типы и тесты, поэтому «у меня работает» невозможно.

**Как проверить.** `make test`.

### 10. Документация и запуск — до 5

**Что требуется.** Полнота исходного кода, инструкция запуска, доступность компонентов. По
документации можно развернуть сервис и повторить демонстрационный сценарий.

**Чем закрыто.**

- **Развёрнутый сервис:** на защите работал по публичному адресу; стенд снят после
  хакатона. Воспроизводится локально одной командой, `/api/health` возвращает
  состояние каждого сервиса.
- **Запуск одной командой:** `make up` собирает образы, поднимает семь сервисов и
  возвращает управление только после прохождения health-проверок. `make demo` показывает
  health, версию и сквозную проверку очереди.
- **Ядро без стека:** `cd core && pip install -e ".[dev]"`, дальше `python -m orbita_core`.
- **Документация** — `docs/`: норматив кейса, ADR, глоссарий, ядро, API, хранение, экраны,
  golden-значения, архитектура одним документом, выводы анализа и этот разбор критериев.
- **Демонстрационный сценарий повторяется** по разделу «Полный цикл через API» в
  `README.md`: от загрузки файла до выгрузки результата и рекомендации, командами `curl`.

**Как проверить.** `make up`, затем команды из `README.md`.
