## 1. Граф отсчёта

Для каждого `t` сетки строится неориентированный граф `G_t = (V_t, E_t)` (ADR-002):

- узлы: активные спутники, клиентские пункты, доступные шлюзы;
- рёбра клиент—спутник и шлюз—спутник: по углу возвышения (`01_SPEC.md` §2.4);
- рёбра спутник—спутник: по дальности и отсутствию пересечения Земли (`01_SPEC.md` §2.5);
- клиентские пункты не транзитные: при обходе из них выходим, в них не входим.

Пакет `orbita_core` (чистый Python + NumPy):

```text
orbita_core/
  scenario.py     загрузка, валидация с JSON path, канонизация, config_hash
  geometry.py     позиции, углы возвышения, ISL (формулы кейса, векторизация по тикам)
  contacts.py     contact plan: словарь рёбер + bitset «отсчёты × рёбра»
  graph.py        adjacency list на отсчёте, Union-Find, компоненты
  routing.py      bfs_shortest, persistent, dijkstra_distance, disjoint_paths
  diagnosis.py    причины разрыва и доказательства
  metrics.py      агрегаты по клиенту и конфигурации, интервалы перерывов
  ranking.py      лексикографическое ранжирование и рекомендация
  export.py       cosmo-A-result-1.0, детерминированная запись и повторная загрузка
  engine.py       оркестрация одного Run, стадии и прогресс, версия ядра
  cli.py          команды run, golden, crosscheck, validate (`python -m orbita_core`)
  __main__.py     точка входа CLI
```

## 1.1 Командная строка

```text
python -m orbita_core run <scenario.json> [--policy bfs_shortest|persistent|dijkstra_distance] [--out <file>]
python -m orbita_core golden <dir> [--fixtures docs/10_FIXTURES.md]
python -m orbita_core crosscheck <scenario.json> --ticks 0,120,43200,86280 [--reference <geometry.py>]
python -m orbita_core validate <scenario.json>
```

`golden` читает ожидания из таблицы `10_FIXTURES.md` §1, а не из копии чисел в коде:
единственный источник golden-значений — документ. `run` печатает метрики и пишет экспорт
по `01_SPEC.md` §8; `crosscheck` сверяет ядро с официальным модулем; код возврата 1 при
любом расхождении или ошибке валидации.

## 2. Pipeline одного Run

1. `scenario.load_and_validate` — ошибки с путём до поля (`03_GLOSSARY.md` §3.6).
2. Канонизация: нормализация углов в [0; 360), объединение пересекающихся интервалов
   недоступности, сортировка списков по `id`; `config_hash` = sha256 канонического JSON +
   `routing_policy`.
3. Геометрия сразу для всех отсчётов: массив позиций `(ticks, N, 3)` в земной системе.
   Для 48 аппаратов и 720 отсчётов это 104 КБ, одна векторная операция.
4. Активность: матрица `(ticks, N)` из `launch_stage` и интервалов отказов.
5. Контакты: матрица возможных ISL-пар и наземных пар; bitset `(ticks, E)`.
6. Маршрутизация по выбранной политике для каждого клиента на каждом отсчёте.
7. Диагностика причин для отсчётов без пути.
8. Метрики и интервалы перерывов.
9. Резервные пути и минимальный разрез (по запросу или для сохранённых Run).
10. Экспорт и передача результата адаптерам хранения (вне ядра).

Производительность на ноутбуке: 4 сценария × 720 отсчётов за 1,6 с в непараллельном
прототипе на `geometry.snapshot`; целевой показатель ядра после векторизации по тикам —
≤ 0,3 с на сценарий из 48 аппаратов. Оценка роста в `06_STORAGE.md` §2.

## 3. Маршрутизация (ADR-003)

### 3.1 `bfs_shortest`
BFS от клиента; соседи-клиенты пропускаются; первый достигнутый доступный шлюз завершает
поиск; путь восстанавливается по `prev`. Сложность `O(V + E)` на отсчёт.

### 3.2 `persistent`
Хранится `current_path[client]`. На отсчёте `t`:
1. если все рёбра `current_path` существуют в `G_t` и шлюз доступен — путь сохраняется;
2. иначе `bfs_shortest`; если путь найден, он становится текущим;
3. если пути нет — `current_path = None`, фиксируется перерыв.
Метрика `route_switches` считает смены пути между соседними отсчётами с путём.
Доступность при этой политике **совпадает** с `bfs_shortest` по построению: инвариант
проверяется тестом.

### 3.3 `dijkstra_distance`
Вес ребра = расстояние в километрах (уже есть в snapshot). Куча с `(dist, node)`.
Используется для сравнения стратегий по суммарной длине и числу переходов.

### 3.4 Независимая проверка достижимости
Union-Find по всем рёбрам `G_t` без клиентских узлов, затем проверка «клиент имеет соседа
в компоненте доступного шлюза». Расхождение с BFS → `INTERNAL_INCONSISTENCY`, Run
помечается `failed`.

### 3.5 Резервные пути и разрез (ADR-007)
Расщепление каждого спутника на `v_in → v_out` с пропускной способностью 1; наземные рёбра
и ISL с пропускной способностью 1; max-flow (Edmonds–Karp достаточно при `V ≤ 2 000`)
от клиента к супер-стоку над доступными шлюзами. Значение потока = `backup_path_count`
(число вершинно-непересекающихся путей). Минимальный разрез = множество критических
аппаратов на отсчёте.

## 4. Диагностика причин (ADR-005)

```text
если нет активных спутников, видимых клиенту          → NO_CLIENT_COVERAGE
если все шлюзы в gateway_outage                         → GATEWAY_OUTAGE
если есть доступные шлюзы и ни один не видит спутник    → NO_GATEWAY_COVERAGE
если и клиент, и доступные шлюзы видят спутники, но
   компоненты этих спутников не пересекаются             → NETWORK_PARTITION
иначе                                                   → INTERNAL_INCONSISTENCY
```

Условия проверяются на непустых множествах: пустое множество видимых спутников не даёт
вакуумного срабатывания `NO_GATEWAY_COVERAGE` или `NETWORK_PARTITION`, оно уже учтено
первыми строками.

Собираются все сработавшие причины; `primary_cause` — первая. Доказательства:
`client_visible_satellites`, `gateway_visible_satellites`, `failed_satellites`,
`client_component_id`, `gateway_component_id`, `last_path` (последний отсчёт с путём до
разрыва), `next_path` (первый после).

## 5. Метрики

### 5.1 По клиенту `c`

```text
availability(c) = reachable_ticks(c) / total_ticks
visibility(c)   = visible_ticks(c) / total_ticks
max_gap_s(c)    = longest_unreachable_run(c) × step_s
mean_hops(c), max_hops(c)   по отсчётам с путём; переход = ребро, включая две наземные линии
route_switches(c)           смены пути между соседними отсчётами, на обоих из которых путь есть;
                            перерыв и выход из него сменой не считаются
outage_intervals(c)         [{start_s, end_s, primary_cause, causes, truncated_by_horizon}]
```

Краевые перерывы входят в `max_gap_s` и помечаются `truncated_by_horizon` (ADR-004).

### 5.2 По конфигурации

`min_client_availability`, `mean_client_availability`, `worst_max_gap_s`, `mean_hops`
(среднее по клиентам от `mean_hops(c)`, клиенты равноправны), `max_hops`,
`route_switches_total`, `outage_count_by_cause`, `backup_path_count_min`
(минимум по клиентам и отсчётам с путём), `target_met_clients` (список клиентов с
`availability ≥ target_availability`).

### 5.3 Диагностические (Resilience X-Ray)

Для каждого спутника `s`: `criticality_delta_availability(s)` и
`criticality_delta_max_gap_s(s)` — изменение `min_client_availability` и `worst_max_gap_s`
при отказе `s` на весь горизонт; `affected_clients(s)`; `min_cut_frequency(s)` — доля
отсчётов, где `s` входит в минимальный разрез хотя бы одного клиента.

## 6. Ранжирование и рекомендация (ADR-006)

Сортировка кандидатов по кортежу
`(−min_client_availability, worst_max_gap_s, −mean_client_availability,
−backup_path_count_min, route_switches_total, mean_hops)`. Рекомендация = лучший кандидат
относительно базового варианта с перечнем изменённых параметров и дельтами по каждому
клиенту. Если целевая доступность не достигнута ни одним кандидатом, рекомендация явно
говорит об этом и показывает ближайшую точку и расстояние до цели.

## 7. Функции v1 на ядре (ADR-013)

| Функция | Что использует из ядра |
|---|---|
| Outage Detective | `diagnosis`, `last_path`/`next_path`, компоненты, отказавшие аппараты рядом с разрывом |
| Design Space Explorer | sweep по `raan_deg`/`phase_deg` одной плоскости или пары «RAAN × phase»; heatmap `min_client_availability`; контур `target_availability` |
| Сравнение | метрики двух и более Run на одной сетке, delta в п. п. и минутах, изменённые параметры |
| Политики маршрутизации | `route_switches`, `mean_hops`, суммарная длина по трём стратегиям |
| Resilience X-Ray | §5.3 |
| Evidence Pack | экспорт + метрики + перерывы + сравнение + рекомендация + `engine_version` |
| Experiment Lineage | `parent_variant_id`, diff, дельты метрик между родителем и потомком |

Sweep: равномерная сетка или Sobol с детерминированным seed, бюджет по числу точек и
времени, локальное уточнение вокруг лучших точек; никаких заявлений о глобальном
оптимуме.

## 8. Тесты ядра

Golden-значения и инварианты вынесены в `10_FIXTURES.md`. Обязательные группы:

- формулы: позиция при `t = 0` совпадает с `geometry.positions`; угол возвышения и ISL
  совпадают с `geometry.snapshot` на выборке отсчётов;
- сетка: первый и последний отсчёт, `horizon_s` не входит;
- интервалы: `start_s` включительно, `end_s` исключительно; объединение пересечений;
- `launch_stage` фильтрует `launch_batch`; недоступный аппарат имеет координаты, но не рёбра;
- `>=` для возвышения, строгое `<` для дальности ISL; линия ISL не пересекает Землю;
- gateway outage; несколько шлюзов; клиент не транзитный;
- каждое ребро каждого экспортированного `path` существует на своём отсчёте;
- BFS и Union-Find согласуются; `persistent` даёт ту же доступность, что `bfs_shortest`;
- повторный запуск одинаковой конфигурации даёт идентичный экспорт;
- некорректный JSON возвращает код ошибки и JSON path;
- скрытый сценарий с другими идентификаторами и числом аппаратов (ADR-015).
