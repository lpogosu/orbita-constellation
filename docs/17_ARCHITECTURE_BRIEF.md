# ОРБИТА. Архитектура и решение в одном документе

Версия 2026-09-12. Самодостаточный документ: содержит всё, что нужно, чтобы отвечать на
вопросы о системе без обращения к другим файлам. Написан для подготовки к разговору с
техническим и отраслевым экспертом.

---

## 1. Что это и для кого

ОРБИТА — веб-сервис для инженера-проектировщика низкоорбитальной спутниковой группировки.
Инженер загружает описание группировки и наземных пунктов, меняет конфигурацию (этап
развёртывания, ориентацию и фазирование плоскостей, периоды отказов аппаратов), запускает
расчёт на сутки и получает: состояние сети в любой момент, маршрут от каждого клиентского
пункта до шлюза, периоды без связи и их причины, показатели доступности, сравнение
вариантов и обоснованную рекомендацию. Результат и использованные параметры выгружаются
в файл заданного формата и могут быть загружены обратно.

Кейс хакатона (КосмоХакатон 2026, «Проектирование устойчивой спутниковой группировки»).
Целевой ориентир кейса: доступность связи не менее 90 % расчётного времени для каждого
клиентского пункта. Это ориентир для исследования, не обязательное условие.

Жюри загрузит собственный сценарий того же формата с другими идентификаторами, числом
аппаратов, плоскостей и координатами. Поэтому в системе нет ничего зашитого под
предоставленные данные: число плоскостей, спутников, клиентов, шлюзов, сетка времени —
всё из файла.

## 2. Входные данные и модель расчёта (норматив кейса)

### 2.1 Формат сценария `cosmo-A-1.0`

| Раздел | Содержание |
|---|---|
| `schema_version` | строка `cosmo-A-1.0` |
| `meta.id`, `meta.title` | идентификатор и название |
| `environment` | `altitude_km` (высота орбиты), `inclination_deg` (наклонение), `earth_angle0_deg` (начальный угол поворота Земли), `horizon_s` (горизонт расчёта), `step_s` (шаг сетки), `min_elevation_deg` (минимальный угол возвышения), `isl_range_km` (дальность межспутниковой линии), `target_availability` (целевая доступность) |
| `design.launch_stage` | этап развёртывания: 1, 2 или 3 |
| `design.planes[]` | плоскости: `id`, `raan_deg` ∈ [0; 360) — долгота восходящего узла, ориентация плоскости; `phase_deg` ∈ [0; 360) — фазирование, общий сдвиг спутников плоскости вдоль орбиты |
| `design.satellites[]` | спутники: `id`, `plane_id`, `slot_deg` (положение в плоскости), `launch_batch` ∈ {1, 2, 3} — очередь запуска |
| `ground_sites[]` | наземные пункты: `id`, `name`, `role` ∈ {`client`, `gateway`}, `lat_deg` ∈ [−90; 90], `lon_deg` ∈ [−180; 180] |
| `failures[]` | отказы спутников: `satellite_id`, `start_s`, `end_s` |
| `gateway_outages[]` | недоступность шлюзов: `gateway_id`, `start_s`, `end_s` |

Предоставленные сценарии: полная группировка (48 аппаратов, 3 плоскости, 3 клиента,
1 шлюз, ISL 3000 км); первая очередь (`launch_stage = 1`, активны 16 аппаратов); десять
отказов (10 аппаратов недоступны с 6-го часа до конца); ISL 2000 км. Плюс наш скрытый
тестовый сценарий с другой структурой: 5 плоскостей по 7 спутников, 2 шлюза, 4 клиента
(один в южном полушарии), отказ шлюза, пересекающиеся отказы спутников.

### 2.2 Константы и орбита

Радиус Земли 6371 км, гравитационный параметр 398600,435507 км³/с², период вращения Земли
86164,09054 с. Круговые орбиты, сферическая Земля. Радиус орбиты `r = R + altitude_km`,
угловая скорость `n = √(μ / r³)`. Аргумент широты спутника `u(t) = slot_deg + phase_deg +
n·t`. Координаты в инерциальной системе через RAAN Ω и наклонение i:

```
x = r·(cos Ω·cos u − sin Ω·sin u·cos i)
y = r·(sin Ω·cos u + cos Ω·sin u·cos i)
z = r·sin u·sin i
```

Переход в систему, связанную с Землёй, поворотом на угол `θ = earth_angle0 + 2π·t/T`.

### 2.3 Сетка времени

Отсчёты `t = 0, step_s, 2·step_s, …, horizon_s − step_s`; правый конец в сетку не входит.
Для базовых сценариев 86400 / 120 = 720 отсчётов. Каждый отсчёт представляет интервал
длиной `step_s`. Все показатели считаются как доли отсчётов.

### 2.4 Контакты

- **Наземный контакт** пункт — спутник: угол возвышения спутника над горизонтом пункта
  **не меньше** `min_elevation_deg`, спутник активен; для шлюза дополнительно нет
  действующей недоступности.
- **Межспутниковый контакт** (ISL): расстояние **строго меньше** `isl_range_km` и отрезок
  между аппаратами не пересекает Землю (ближайшая к центру Земли точка отрезка дальше R).
- **Активность аппарата:** `launch_batch ≤ launch_stage` и нет действующего отказа.
  Интервалы отказов `[start_s; end_s)`: начало включительно, конец исключительно;
  пересекающиеся объединяются. Недоступный аппарат сохраняет координаты, но исключается
  из всех связей.

### 2.5 Маршрут

Контакты двунаправленные. Маршрут начинается в клиентском пункте, проходит через один или
несколько активных спутников, заканчивается в доступном шлюзе. Клиентские пункты не
ретранслируют (промежуточные узлы только спутники). Маршрут рассматривается для текущего
отсчёта целиком. Способ поиска и обновления выбирает команда; любой допустимый маршрут
принимается. Пропускная способность, задержки и ожидание будущего контакта в обязательную
модель не входят.

### 2.6 Показатели по клиентскому пункту

| Показатель | Определение |
|---|---|
| Видимость | доля отсчётов, где виден хотя бы один активный спутник |
| Доступность | доля отсчётов, где существует путь до шлюза |
| Максимальный перерыв | самая длинная последовательность отсчётов без пути × `step_s` |
| Число переходов | рёбра маршрута, включая две наземные линии |

Видимость не гарантирует доступность: спутник над пунктом может быть, а пути до шлюза
через сеть — нет. Это центральная мысль продукта.

### 2.7 Формат выгрузки `cosmo-A-result-1.0`

```json
{ "schema_version": "cosmo-A-result-1.0",
  "effective_scenario": { "...полный использованный сценарий..." },
  "routes": [ { "t_s": 120, "client_id": "…", "path": ["клиент", "спутник", "…", "шлюз"] },
              { "t_s": 240, "client_id": "…", "path": [] } ] }
```

Для каждой пары «отсчёт — клиент» ровно одна запись; пустой `path` — маршрута нет.
Мы добавляем сводные метрики, перерывы, версию ядра, политику маршрутизации, хеш
конфигурации.

## 3. Ядро расчёта: как устроено

Ядро — чистая библиотека на Python 3.12 и NumPy без единого импорта из HTTP, ORM, Redis
или файловых хранилищ. Пакет `orbita_core`, модули: `scenario`, `geometry`, `contacts`,
`graph`, `routing`, `diagnosis`, `metrics`, `ranking`, `compare`, `export`, `engine`, `cli`.

### 3.1 Конвейер одного расчёта

1. **Загрузка и валидация.** Все правила проверяются сразу, ошибки возвращаются списком, у
   каждой код и путь до поля в точечной нотации (`design.planes[1].raan_deg`). Коды:
   `UNSUPPORTED_SCHEMA_VERSION`, `INVALID_SCENARIO_FIELD`, `DUPLICATE_NODE_ID`,
   `UNRESOLVED_REFERENCE`, `INVALID_TIME_GRID`, `INVALID_OUTAGE_INTERVAL`,
   `MISSING_SITE_ROLE`. Границы те же, что в официальном модуле: высота 200–1200 км,
   наклонение (0; 180], горизонт ≤ 172 800 с, угол возвышения [0; 90), ISL (0; 10 000] км.
2. **Канонизация.** Углы нормализуются в [0; 360), пересекающиеся и смежные интервалы
   отказов одного аппарата объединяются, списки сортируются по `id`, JSON записывается
   детерминированно. `config_hash` = SHA-256 канонического JSON плюс политика
   маршрутизации. Одна конфигурация всегда даёт один хеш и один результат.
3. **Геометрия сразу для всех отсчётов.** Массив позиций `(отсчёты, N, 3)` в земной
   системе одной векторной операцией. Для 48 аппаратов и 720 отсчётов это 2 мс.
4. **Активность.** Матрица `(отсчёты, N)` из этапа запуска и интервалов отказов; матрица
   доступности шлюзов.
5. **Контакты.** Для всех пар «пункт — спутник» углы возвышения, для всех пар «спутник —
   спутник» расстояния и проверка пересечения Земли, векторно по времени. Результат —
   contact plan: список возможных рёбер (с типом `ground`/`isl`), битовая матрица
   `(отсчёты, рёбра)` и матрица расстояний. Для полной группировки 34 КБ битов, после
   сжатия около 5 КБ. Построение около 70 мс.
6. **Маршрутизация** по выбранной политике для каждого клиента на каждом отсчёте (§3.2).
7. **Диагностика причин** на отсчётах без пути (§3.3).
8. **Метрики и интервалы перерывов** (§3.4).
9. **Резервные пути и минимальный разрез** (§3.5).
10. **Экспорт** и передача результата хранилищам (вне ядра).

Время полного расчёта суток для 48 аппаратов около 0,25 с. На плотной сетке: 2880
отсчётов — 1,1 с, 8640 отсчётов — 4,6 с.

### 3.2 Граф отсчёта и маршрутизация

На каждом отсчёте строится неориентированный граф: узлы — активные спутники, клиенты,
доступные шлюзы; рёбра — из contact plan. Список смежности собирается из битовой
матрицы без обхода всех пар. Клиенты не транзитные: из клиента выходим, в клиент не
входим.

Три политики маршрутизации, все на одном графе:

| Политика | Что делает | Зачем |
|---|---|---|
| `bfs_shortest` (по умолчанию) | поиск в ширину от клиента до любого доступного шлюза, минимум переходов, пересчёт на каждом отсчёте | прозрачный baseline; доказывает достижимость |
| `persistent` | текущий маршрут сохраняется, пока все его рёбра существуют и шлюз доступен; при разрыве новый поиск | это и есть «обновление маршрута» из критериев жюри: меньше перестроений; доступность совпадает с BFS по построению |
| `dijkstra_distance` | Дейкстра с весом ребра = длина линии в км | сравнение стратегий, прокси задержки распространения |

Метрика `route_switches` — число смен пути между соседними отсчётами, на обоих из
которых путь есть; перерыв и выход из него сменой не считаются.

**Независимая проверка.** Достижимость каждого клиента дополнительно проверяется
структурой «система непересекающихся множеств» (Union-Find) по всем рёбрам без клиентских
узлов: клиент достижим, если у него есть сосед-спутник в компоненте какого-либо
доступного шлюза. Расхождение с BFS помечает расчёт ошибкой `INTERNAL_INCONSISTENCY`
вместо выдачи правдоподобного ответа. Алгоритмы графов написаны свои (BFS, Union-Find,
Дейкстра, Эдмондс — Карп); NetworkX используется только в тестах как оракул.

### 3.3 Причины отсутствия маршрута

Проверяются по порядку, собираются все сработавшие, первая — главная:

| Причина | Условие |
|---|---|
| `NO_CLIENT_COVERAGE` | у клиента нет ни одного видимого активного спутника |
| `GATEWAY_OUTAGE` | все шлюзы в периоде недоступности |
| `NO_GATEWAY_COVERAGE` | есть доступные шлюзы, но ни один не видит спутник |
| `NETWORK_PARTITION` | и клиент, и шлюзы видят спутники, но эти спутники в разных компонентах связности |
| `INTERNAL_INCONSISTENCY` | путь не найден, но ни одна причина не сработала: ошибка расчёта |

К причине прикладываются доказательства: спутники, видимые клиенту; спутники, видимые
шлюзам; аппараты в отказе на этом отсчёте; идентификаторы компонент связности клиента и
шлюза; последний рабочий маршрут до разрыва и первый после.

### 3.4 Метрики

По клиенту: доступность, видимость, максимальный перерыв, среднее и максимальное число
переходов (по отсчётам с путём), число перестроений, признак достижения цели, число
перерывов по причинам, список интервалов перерывов `[start_s; end_s)` с причиной и флагом
`truncated_by_horizon` (перерыв примыкает к началу или концу суток; такие перерывы
входят в максимальный, но помечены — трактовка команды для фразы кейса «учитываются
отдельно»).

По конфигурации: минимальная и средняя доступность по клиентам, худший максимальный
перерыв, среднее и максимальное число переходов, суммарные перестроения, минимальное число
резервных путей, число перерывов по причинам, список клиентов, достигших цели.

### 3.5 Резервные пути и критические аппараты

На отсчёте считается число вершинно-непересекающихся путей клиент → шлюз: каждый спутник
расщепляется на вход и выход с пропускной способностью 1, все рёбра с пропускной
способностью 1, максимальный поток (Эдмондс — Карп) от клиента к супер-стоку над
доступными шлюзами. Величина потока = `backup_path_count`. Минимальный вершинный разрез =
множество аппаратов, без которых связи нет. Для сценария из 48 аппаратов полный подсчёт
на всех отсчётах и клиентах занимает около 0,3 с.

Планируемое расширение (в работе): критичность каждого аппарата контрфактическим
прогоном — отказ аппарата на весь горизонт, дельта худшей доступности и худшего перерыва,
затронутые клиенты, доля отсчётов в минимальном разрезе; мосты и двусвязные компоненты
графа отсчёта (Тарьян).

### 3.6 Ранжирование и рекомендация

Кандидаты сравниваются лексикографически: 1) максимум минимальной доступности по
клиентам; 2) минимум худшего максимального перерыва; 3) максимум средней доступности;
4) максимум резервирования; 5) минимум перестроений; 6) минимум переходов. Порядок
показывается рядом с рекомендацией. Рекомендация — лучший кандидат относительно базового
варианта с перечнем изменённых параметров (из diff сценариев) и дельтами по каждому клиенту
в процентных пунктах и секундах, с ограничениями (сетка, горизонт, ISL). Если целевая
доступность не достигнута ни одним кандидатом, рекомендация говорит об этом явно.
Генеративные модели в расчётах и рекомендациях не участвуют: все выводы детерминированы
из метрик.

### 3.7 Сравнение «до и после отказа»

Для двух расчётов на одной сетке: по клиенту — новые, исчезнувшие и изменившиеся перерывы
с границами обеих сторон, причиной и отказавшими аппаратами; число отсчётов, где маршрут
сохранился узел в узел и где перестроен; первый отсчёт расхождения; первый новый перерыв;
список затронутых клиентов. На паре «полная группировка — десять отказов» дельты
совпадают с эталонной таблицей.

### 3.8 Экспорт

`build_export` формирует `cosmo-A-result-1.0`: `routes` ровно `отсчёты × клиенты` записей
в фиксированном порядке, `effective_scenario` канонический, плюс метрики, перерывы,
версия ядра, политика, хеш. Запись детерминированная: повторный запуск даёт байт в байт
тот же файл. `load_export` проверяет схему, валидирует сценарий, число записей и
отсутствие дубликатов; повторный расчёт из выгрузки даёт тот же `config_hash`.

### 3.9 Командная строка ядра

```
python -m orbita_core run <scenario.json> [--policy …] [--out <file>]
python -m orbita_core golden <dir>            сверка с эталонной таблицей значений
python -m orbita_core crosscheck <json> --ticks 0,120,43200,86280   сверка с официальным geometry.py
python -m orbita_core validate <json>         ошибки списком с кодами и путями
```

## 4. Платформа

### 4.1 Сервисы (docker compose, семь контейнеров)

| Сервис | Работа сейчас | Роль при росте |
|---|---|---|
| `api` (FastAPI, Python 3.12, uvicorn) | валидация, проекты, варианты, запуски, результаты, SSE, экспорт | без состояния, реплики за балансировщиком |
| `worker` (arq на Redis) | суточные расчёты, эксперименты, критичность | N воркеров = N параллельных задач |
| `postgres` 16 | проекты, варианты, запуски, метрики, перерывы, точки экспериментов, журнал задач, артефакты | транзакции, индексы, аналитика по тысячам запусков |
| `redis` 7 | очередь задач, прогресс запуска (pub/sub → SSE), кэш предпросмотра, ключи идемпотентности, флаги отмены | низкая задержка, TTL |
| `memgraph` + MAGE | контакты сохранённых запусков интервалами, происхождение вариантов, графовые алгоритмы | in-memory графы, Cypher, Bolt |
| `minio` | сжатые трассы, выгрузки, evidence pack | объекты с TTL и версиями |
| `web` (nginx) | статика React, reverse proxy на api, SSE без буферизации | отдельный релиз фронтенда |

`docker compose up` (или `make up`) поднимает все семь; `/api/health` показывает состояние
каждого и флаг `degraded_mode`.

### 4.2 Сущности

- **Project** — контейнер исследования: варианты, запуски, эксперименты.
- **Variant** — неизменяемая версия сценария; хранит `parent_variant_id` и `diff_from_parent`
  (список `{path, from, to}`, сравнение канонических сценариев по `id` элементов, а не по
  позиции), `config_hash` сценария. Редактирование в интерфейсе создаёт черновик;
  сохранение — новый Variant. Это и есть происхождение вариантов.
- **Run** — выполнение расчёта конкретного варианта конкретной версией ядра и политикой:
  `status` (`queued → running → succeeded | failed | cancelled`), `stage` (`validate →
  geometry → contacts → routing → analytics → persist → complete`), прогресс, `config_hash`,
  `engine_version`, `trace_uri`, `degraded_mode`, ошибка со стадией.
- **ClientMetrics**, **ConfigMetrics**, **OutageInterval** — результаты в Postgres.
- **Experiment / ExperimentPoint** — перебор конфигураций (в работе).
- **Recommendation**, **Artifact**, **Job** — служебные.

### 4.3 Жизненный цикл запуска

1. `POST /api/runs {variant_id, routing_policy}` с необязательным заголовком
   `Idempotency-Key`. Если ключ уже есть в Redis — возвращается тот же Run (200); тот же
   ключ с другим телом — 409. Если существует успешный Run с тем же `config_hash` и
   `engine_version` — он переиспользуется (200) без расчёта. Иначе создаётся Run (202) и
   задача ставится в arq с идентификатором задачи = идентификатор Run (очередь не дублирует).
2. Воркер выполняет расчёт ядра в отдельном потоке, чтобы цикл событий оставался живым для
   отмены и heartbeat. Колбэк прогресса публикует стадию и число отсчётов в Redis-канал
   `run:{id}` и обновляет Postgres не чаще раза в 0,5 с.
3. Метрики, перерывы и статус пишутся одной транзакцией. Затем артефакты: трасса
   (`trace.bin`) и выгрузка (`export.json`) в MinIO, узлы и контакты интервалами в
   Memgraph, записи в таблице артефактов с TTL.
4. Ошибка расчёта детерминирована, поэтому не повторяется: Run → `failed` с кодом и
   стадией. Ошибки инфраструктуры (БД, Redis) повторяются очередью до трёх раз.
5. Отмена: флаг в Redis проверяется между стадиями; в очереди — сразу `cancelled`.
6. `GET /api/runs/{id}/events` — SSE: текущее состояние, затем события pub/sub, heartbeat
   раз в 15 с, завершение на терминальном статусе; при недоступном Redis — опрос Postgres.

Уникальный индекс `runs(config_hash, engine_version)` частичный: только для `queued`,
`running`, `succeeded`, чтобы упавший или отменённый запуск можно было повторить.

### 4.4 Хранение

- **Postgres**: `projects`, `variants` (сценарий jsonb, diff jsonb, хеш), `runs`,
  `client_metrics`, `config_metrics`, `outage_intervals` (с причинами и доказательствами
  jsonb), `experiments`, `experiment_points`, `recommendations`, `jobs`, `artifacts`.
  Миграции Alembic применяются при старте api.
- **Redis**: `arq:queue`; `run:{id}` (pub/sub прогресса); `run:{id}:cancel` (TTL 1 ч);
  `preview:{config_hash}:{t_s}` (TTL 1 ч); `idem:{key}` (TTL 24 ч).
- **MinIO**, бакет `orbita`: `runs/{id}/trace.bin` (contact plan: узлы, рёбра, битовая
  матрица; упаковка битов и сжатие zstd), `runs/{id}/export.json`, `runs/{id}/evidence.zip`.
  Координаты не хранятся: восстанавливаются из сценария и времени. TTL: несохранённые
  интерактивные запуски 24 ч, трассы точек перебора 7 дней, сохранённые варианты — до
  удаления проекта. После истечения TTL трасса пересчитывается детерминированно.
- **Memgraph**: `(:Run {id, engine_version, routing_policy})-[:HAS_NODE]->(:Node {run_id,
  node_id, kind, plane_id})`; `(:Node)-[:CONTACT {run_id, start_tick, end_tick,
  min_distance_km, max_distance_km}]->(:Node)` — контакты интервалами `[start; end)` по
  непрерывным сериям единиц битовой матрицы; `(:Variant)-[:DERIVED_FROM {diff,
  дельты}]->(:Variant)`. Запросы: какие аппараты входят во все пути клиента в интервале;
  мосты и двусвязные компоненты (MAGE); путь происхождения варианта. Запись идемпотентна.

### 4.5 Degraded mode

Все внешние хранилища доступны только через адаптеры с общим интерфейсом:
`ArtifactStore` (MinIO или локальный каталог), `GraphStore` (Memgraph или пустой адаптер),
очередь (arq или выполнение в фоне процесса api). Реестр выбирает реализацию по
доступности с таймаутом 1 с (`ORBITA_STORAGE_MODE = auto | local | full`). При
недоступности Redis, Memgraph или MinIO одиночный расчёт проходит целиком, ответ и Run
помечаются `degraded_mode: true`; сбой адаптера после расчёта не откатывает уже
записанные метрики. Отдельный compose-профиль `degraded` проверяет это. На защите
основной режим — полный.

### 4.6 Оценка роста

| Показатель | N = 48 | N = 500 | N = 2000 |
|---|---:|---:|---:|
| ISL-пар на отсчёт | 1 128 | 124 750 | ~2 млн |
| Проверок ISL за сутки | 0,8 млн | 90 млн | 1,4 млрд |
| Время суток, одно ядро | ~0,25 с | секунды | десятки секунд без отсева |
| Трасса до сжатия | 34 КБ | ~11 МБ | ~180 МБ |

Выводы: при N ≥ 500 нужен пространственный отсев кандидатов ISL (сетка или KD-дерево:
пары с O(N²) до O(N·k)); трасса при таких размерах не помещается в строку БД — отсюда
объектное хранилище; перебор конфигураций и критичность — независимые задачи, их
масштабирует число воркеров, а не скорость одного ядра.

Лимиты: JSON ≤ 10 МБ, N ≤ 5000, точек перебора ≤ 2000, время перебора ≤ 30 мин.

## 5. API

Контракт — OpenAPI, генерируется из схем Pydantic; из него генерируются типы для
фронтенда; тест сверяет множество путей с документом. Ошибки в одном конверте:
`{"error": {"code", "message", "path", "details"}}`, валидация возвращает `{"errors": [...]}`
целиком. HTTP: 400 вход, 404 нет сущности, 409 конфликт идемпотентности или отмены
завершённого, 422 превышение бюджета перебора, 503 хранилище недоступно.

| Группа | Endpoint |
|---|---|
| Проекты и варианты | `POST /api/scenarios/validate`; `POST /api/projects`; `GET /api/projects`; `GET /api/projects/{id}`; `POST /api/projects/{id}/variants`; `GET /api/variants/{id}`; `GET /api/variants/{id}/export`; `GET /api/projects/{id}/lineage` |
| Расчёт | `POST /api/preview` (снимок одного отсчёта для черновика без Run, кэш 1 ч); `POST /api/runs`; `GET /api/runs/{id}`; `GET /api/runs/{id}/events` (SSE); `POST /api/runs/{id}/cancel` |
| Результат | `GET /api/runs/{id}/snapshot?t_s=` (спутники с координатами и активностью, рёбра с типом и длиной, клиенты с маршрутом и причиной); `…/timeline` (битовые маски доступности и видимости по клиентам, причины по отсчётам); `…/metrics`; `…/outages`; `…/backup-paths?t_s=&client_id=`; `…/export`; `…/evidence-pack` (zip: выгрузка, метрики, перерывы, сравнение, рекомендация) |
| Сравнение и исследования | `POST /api/comparisons {run_ids}` (база — первый; метрики рядом, дельты, изменённые параметры, разбор перерывов до/после); `GET /api/runs/{id}/recommendation?base_run_id=`; `POST /api/experiments`, `GET /api/experiments/{id}`, `GET …/points`, `POST …/points/{point_id}/materialize` (в работе); `POST /api/analysis/criticality` (в работе) |
| Служебные | `GET /api/health`; `GET /api/version`; `GET /api/openapi.json` |

Полный цикл без интерфейса проверен на всех сценариях: validate → project → run (SSE) →
snapshot → timeline → metrics → outages → backup-paths → export → повторная валидация
выгрузки → второй вариант → comparisons → recommendation → evidence-pack.

## 6. Интерфейс

React 18 + TypeScript strict, Vite, Tailwind на CSS-переменных из токенов Figma, типы из
OpenAPI, ECharts для графиков, Canvas 2D для карты. Интерфейс ничего не считает: все
числа из API; ни одного идентификатора или значения с макетов в коде.

Экран верстается как полотно 1920×1080 с точными размерами из макета и целиком
масштабируется под окно (`min(ширина/1920, высота/1080)`), поэтому на 2K и на 1366 px он
выглядит как макет, только крупнее или мельче; прокрутка только внутри карточек; поля
по краям на нестандартных пропорциях заполняет продолжение фоновой сцены.

Разделы: **Проекты** (загрузка JSON перетаскиванием, четыре примера, сводка сценария из
API, ошибки списком с путями, недавние проекты, создание проекта); **Сеть** (панель
конфигурации: этап, RAAN и фаза плоскостей, политика, отказы; предпросмотр черновика; запуск
с прогрессом по стадиям; карта в полярной проекции: плоскости, спутники, контакты, клиенты,
шлюз, маршрут, резервный маршрут, компоненты; карточки клиентов с причиной разрыва и
доказательствами; таймлайн по клиентам с воспроизведением и причинами оттенками);
**Отказы** (список отказов, выбор спутника с карты, до/после, затронутые клиенты, первый
момент расхождения, критические аппараты); **Сравнение** (два и более варианта, дельты в
п. п. и минутах, изменённые параметры из diff, шкалы рядом, рекомендация с порядком
критериев, сравнение политик); **Результат** (метрики, перерывы, параметры расчёта,
выгрузки); **Исследования** (перебор по RAAN и фазе с бюджетом, тепловая карта с контуром
цели, лучшие точки, сохранение точки как варианта); **Проект** (варианты, запуски,
происхождение).

Состояния каждого блока: загрузка, пусто, ошибка с повтором, недоступно; после правки
черновика результаты помечаются устаревшими; при недоступности хранилищ — баннер
деградации; индикатор идущего расчёта с отменой в шапке.

Состояние на 2026-09-12: каркас и экран «Проекты» в основной ветке и работают на живом
API; остальные экраны переносятся из утверждённых макетов Figma.

## 7. Что и как проверено

- **Сверка с официальным модулем** `geometry.py`: позиции на отсчётах 0, 120, 43200, 86280
  всех сценариев совпадают с точностью 9·10⁻¹³ км; множества рёбер совпадают побитово.
- **Эталонные значения** (получены независимым пересчётом на официальном модуле): 48
  значений — доступность, видимость, максимальный перерыв, среднее число переходов для
  трёх клиентов четырёх сценариев — совпадают без подгонки. Например, полная группировка:
  доступности 0,9667 / 0,9875 / 0,9889, максимальные перерывы 480 / 120 / 120 с; первая
  очередь: 0,2722 / 0,1583 / 0,1264; десять отказов: 0,7931 / 0,8083 / 0,8250; ISL 2000 км:
  0,7750 / 0,6222 / 0,6514.
- **Инварианты** на всех сценариях: каждое ребро каждого маршрута существует на своём
  отсчёте; концы маршрута — клиент и доступный шлюз, промежуточные — активные спутники;
  BFS и Union-Find согласованы; доступность при удержании маршрута равна доступности BFS;
  перестроений при удержании не больше; переходов у BFS не больше, чем у Дейкстры;
  видимость ≥ доступности; отказ на весь горизонт не повышает доступность; число записей
  выгрузки = отсчёты × клиенты; выгрузка проходит валидацию и даёт тот же файл;
  интервалы отказов `[a; b)`; краевые перерывы помечены; сумма перерывов =
  (1 − доступность) × горизонт; резервных путей ≥ 1 там, где есть путь.
- **Свойства на случайных графах** против NetworkX: достижимость, длина кратчайшего пути,
  число непересекающихся путей, минимальный разрез; мосты и точки сочленения.
- **Негативные фикстуры**: 11 файлов с ошибками возвращают ожидаемый код и путь; файл с
  тремя ошибками возвращает три.
- **Скрытый сценарий** с другой структурой проходит весь цикл через API без правки кода.
- **Независимые ревью**: два ревьюера с чистым контекстом пересчитали четыре сценария по
  официальному модулю своим кодом, проверили 8640 маршрутов из выгрузок на существование
  рёбер, прошли полный цикл через API и degraded-режим, сверили OpenAPI с документом.
  Этапы «ядро» и «платформа» приняты.
- Объём проверок: ядро 385 тестов, API 129, воркер 8; `ruff` и `mypy --strict` чистые.

## 9. Ключевые решения и отвергнутые альтернативы

| Решение | Почему | Отвергнуто |
|---|---|---|
| Ядро первично, интерфейс вторичен | 15 + 15 + 10 баллов технических критериев набираются расчётом; интерфейс без корректных чисел бесполезен | идти от экранов на мок-данных |
| 720 мгновенных графов на сетке, contact plan как битовая матрица | кейс требует маршрут целиком в текущем отсчёте; сопоставимость вариантов на одной сетке; килобайты вместо мегабайт | непрерывная модель контактов с точными моментами входа/выхода; 720 JSON-снимков |
| BFS как baseline, удержание маршрута как политика обновления, Дейкстра для сравнения | рёбра невзвешенные, «лучше» без определения веса не обосновано; удержание маршрута измеримо через перестроения | Дейкстра как единственный алгоритм; маршрут с заглядыванием в будущие контакты (использует недоступную в отсчёте информацию) |
| Union-Find как независимая проверка достижимости | расхождение алгоритмов лучше поймать, чем выдать правдоподобный ответ | — |
| Краевые перерывы входят в максимальный и помечаются | исключение занижает показатель | исключать краевые перерывы |
| Причины разрыва с доказательствами | кейс требует показывать причину; доказательства делают её проверяемой | текст «маршрут отсутствует» |
| Лексикографическое ранжирование | эксперты не назвали веса; постановщик: доступность — ключевой показатель; один агрегированный балл скрывает компромисс | взвешенная сумма |
| Резервные пути через max-flow с расщеплением вершин | прямой эффект на обязательные метрики, понятен отраслевому эксперту | только betweenness centrality |
| Семь сервисов с реальной работой у каждого | вопросы эксперта о масштабировании и хранении графов; production-состав сразу | `api + postgres`; Celery вместо arq |
| Memgraph с MAGE | in-memory, быстрый старт, Cypher и Bolt, графовые алгоритмы из коробки; для расчёта необязателен | Neo4j Community (JVM, медленный старт, алгоритмы отдельным плагином); Postgres как хранилище графов |
| Трассы как bitset в объектном хранилище, метрики в Postgres | сотни МБ на один перебор при снимках JSON; координаты восстанавливаются | 720 снимков на запуск |
| `config_hash` + версия ядра | воспроизводимость и дедупликация запусков; происхождение вариантов через diff | — |
| Без генеративных моделей в расчётах и рекомендациях | ни один критерий не даёт за это баллов; ошибка в цифре обнуляет доверие; внешний ключ — точка отказа на защите | «ИИ-ассистент» как функция v1 |
| Карта в полярной азимутальной проекции на Canvas 2D | пункты северные; читаемость подписей и маршрутов; 3D — позже переключателем | 3D как единственный режим |
| Скрытый сценарий с другой структурой в тестах | жюри загрузит свой файл | тестировать только на четырёх файлах |
| Полотно 1920×1080 с масштабом под окно | дизайн утверждён как одно полотно; резиновая вёрстка ломала пропорции и вытесняла кнопки | адаптивная вёрстка со сжатием блоков |

## 10. Ограничения, которые называем сами

- Сетка и горизонт из файла (обычно 120 с и 24 ч); правый конец интервала не считается.
- Пропускная способность, задержки, очереди, ожидание будущего контакта не моделируются.
- Перебор конфигураций — равномерная сетка по одному-двум параметрам, не глобальная
  оптимизация; формулировка «наблюдаемая зависимость на рассчитанных точках».
- Рекомендация детерминированная; если цель не достигнута, так и сказано.
- Рельеф, застройка, физика радиоканала не учитываются (постановщик назвал это «задачей
  со звёздочкой»; дешёвое расширение — маска горизонта или свой угол возвышения по пункту).
- При сотнях аппаратов нужен пространственный отсев ISL-пар; сейчас полный перебор пар.
- Публичный деплой для доступа жюри после стоп-кода — отдельный шаг, ещё не сделан.

## 11. Готовые ответы на вероятные вопросы

**Почему BFS, а не Дейкстра?** Рёбра обязательной модели невзвешенные, любой допустимый
маршрут принимается; BFS даёт минимум переходов и прозрачно доказывает достижимость.
Дейкстра по длине линий есть как третья политика для сравнения стратегий, и мы явно
говорим, что «лучше» без определения веса не бывает.

**Как вы «обновляете» маршрут, а не только ищете?** Политика удержания: маршрут сохраняется,
пока все его рёбра существуют и шлюз доступен, иначе новый поиск. Разница измеряется
числом перестроений; доступность при этом не меняется, что проверено тестом.

**Как вы уверены, что расчёт верный?** Три уровня: сверка позиций и рёбер с официальным
модулем на выборке отсчётов (расхождение 10⁻¹² км); 48 эталонных значений, полученных
независимым пересчётом; свойства на случайных графах против NetworkX. Плюс два независимых
ревью, пересчитавших всё своим кодом.

**Что если у жюри другое число плоскостей, шлюзов или другая сетка?** Всё берётся из
файла. Скрытый сценарий с 5 плоскостями, 35 аппаратами, 2 шлюзами и южным клиентом
проходит весь цикл. Сетка 8640 отсчётов считается за 4,6 с.

**Где хранятся графы?** Расчёт — в памяти ядра как битовая матрица контактов. Трасса —
объект в MinIO. Графовые запросы и происхождение — в Memgraph, контакты интервалами.
Метрики — в Postgres. Расчёт от графовой БД не зависит.

**Что будет, если Redis, MinIO или Memgraph упадут?** Одиночный расчёт проходит целиком
через локальные адаптеры, ответ помечается `degraded_mode`. Проверено отдельным профилем
и ревью.

**Как масштабировать на 500 и больше аппаратов?** Пространственный отсев ISL-кандидатов
(O(N·k) вместо O(N²)), объектное хранилище для трасс, число воркеров для перебора и
критичности. Таблица роста в §4.6.

**Почему не хранить снимки сети на каждом отсчёте?** 720 снимков JSON на каждую точку
перебора — сотни мегабайт; битовая матрица — килобайты, а координаты восстанавливаются
из сценария и времени детерминированно.

**Как объясняется разрыв?** Четыре причины по порядку проверки с доказательствами: кто
кого видит, кто в отказе, компоненты связности, последний и следующий рабочий маршрут.
Если ни одна причина не сработала, а пути нет, расчёт помечается ошибочным.

**Как выбирается рекомендация?** Лексикографически: худший клиент, худший перерыв,
средняя доступность, резервы, перестроения, переходы. Порядок показывается пользователю.
Дельты по каждому клиенту и перечень изменённых параметров из diff вариантов. Без
генеративных моделей.

**Краевые перерывы?** Входят в максимальный перерыв, помечены флагом и в интерфейсе
подписаны «обрезан границей расчёта». Исключать их значило бы занижать показатель.

**Что с лицензиями?** Весь стек свободный. Memgraph под BSL: нельзя предоставлять как
DBaaS, для внутреннего инструмента не мешает. MinIO архивирован в 2026 году: в production
заменяется на SeaweedFS через тот же S3-адаптер.

**Сколько стоит и когда окупится?** Пилот 4 FTE за 4 месяца, 5,7 млн ₽; инфраструктура
17 тыс. ₽/мес; окупаемость 22,5 месяца при 400 вариантах в год, порог 112 вариантов в год.
Единственное допущение, двигающее окупаемость, — часы инженера на вариант; его просим
уточнить.

**Что не сделано?** Перебор конфигураций и критичность аппаратов на бэкенде в работе;
интерфейс переносится из макетов; публичный деплой; маска горизонта по пунктам как
расширение.

## 12. Словарь

Contact plan — список возможных контактов с интервалами их существования; у нас —
битовая матрица «отсчёты × рёбра». ISL — межспутниковая линия. RAAN — долгота
восходящего узла, ориентация плоскости. Фазирование — сдвиг спутников плоскости вдоль
орбиты. Этап развёртывания — сколько очередей запуска выведено. Видимость — есть спутник
над пунктом. Доступность — есть путь до шлюза. Перерыв — непрерывная последовательность
отсчётов без пути. Union-Find — структура для проверки связности без поиска пути.
Max-flow с расщеплением вершин — способ посчитать непересекающиеся по спутникам
маршруты. `config_hash` — отпечаток конфигурации. Evidence pack — архив с выгрузкой,
метриками, перерывами, сравнением и рекомендацией. Degraded mode — работа без внешних
хранилищ через локальные адаптеры.
